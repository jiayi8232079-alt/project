## 0. 先说清楚边界

### 用户端 App（C 端家庭）

给老人家属、监护人、下单用户使用。用户能看到：

- 家庭看护盘：老人状态、设备状态、告警、用药、健康趋势。
- 告警与通知：SOS、跌倒、漏服、设备离线、社区通知、服务订单。
- 家庭能力：成员、权限、声纹、家属投喂、家庭任务。
- 服务能力：陪诊、家政、维修、助浴、理发、陪护、康复等可下单服务。
- 合作医院：可展示的合作医院、科室、复诊/随访、陪诊衔接。
- 隐私授权：健康、对话摘要、视频、记忆、社区可见范围。

用户端不应该看到：

- 社区全部老人列表。
- 服务商内部结算和资质审核。
- B 端公司对账、SLA、合同。
- 其他家庭的设备、告警和健康数据。

### 社区后台（独立社区门户）

给社区、街道、养老机构值班员使用。社区后台管理：

- 本社区/本机构老人和设备。
- 社区内容发布、审核、撤回、播报回执。
- SOS/跌倒/漏服/离线等告警值班和处置。
- 重点老人标签、回访任务、上门探访记录。
- 社区项目报表：覆盖率、在线率、告警响应、消息触达率。

社区后台不应该管理：

- 平台全局套餐、分账、发票。
- 全部 B 端公司合同。
- 其他社区/机构的数据。
- 用户家庭私密陪伴记忆全文。

### B 端公司后台 / 企业门户

给合作服务商、家政公司、陪诊公司、医院合作方、代理商使用。B 端用：

- 服务商资料、资质、服务区域、服务项目、价格。
- 服务订单履约：接单、派人、上门、完成、上传凭证、评价投诉。
- 合作医院资源：协议、科室、权益、转诊/随访配置。
- 对账、结算、SLA、服务质量统计。
- 企业/代理项目报备、客户设备、售后工单。

B 端不应该看到：

- 用户完整健康档案，除非该订单/服务授权需要。
- 社区全量项目管理数据。
- 平台全局运营数据。
- 老人私人对话和陪伴记忆。

### 平台总后台

给公司运营、客服、财务、技术使用。平台能跨租户管理：

- 租户、角色、权限、系统配置。
- 全局设备、告警、服务商、医院、计费、AI 质检。
- 社区/企业/政府门户配置。
- 数据审计、异常处理、全局报表。

## 1. 现有系统适配判断

现有文档显示系统可以适配这套分工：

- 多租户已有 `platform / government / community / enterprise` 门户模型，可承接社区后台和 B 端公司后台。
- 后台已有订单、客户、护工、财务、告警、设备、计费、AI、租户和四门户大屏基础。
- App 已有登录、订单、用药、告警、AI 对话、家庭、健康、会员和设备 mock 基础。
- 后端 API 已有 `orders`、`professional-services`、`hospitals`、`family`、`alerts`、`devices`、`billing`、`tenants` 等基础。

主要缺口：

- 社区内容触达缺新模块。
- 服务商/B 端公司履约缺完整后台。
- 声纹成员、家庭任务、投喂、设备设置、推送 token、视觉跌倒处置、应急升级缺接口和页面。
- 当前工作树大量源码处于删除状态；开发前需确认源码位置或恢复，否则只能按文档和 mock 契约推进。

## 2. 五个 AI 并行分工

### AI-1：后端接口与数据模型

负责范围：

- 新增/补齐接口：`/app/device-token`、`/device-settings`、`/voiceprints`、`/family/family-messages`、`/family/tasks`、`/community-content`、`/content-deliveries`、`/alerts/fall-events`、`/emergency-dispatch`、`/service-providers`、`/hospital-partnerships`。
- 数据模型：社区内容、触达回执、设备设置、声纹授权、家庭任务、服务商、合作医院协议、应急处置记录。
- 权限：按 tenant、community、enterprise、family 做数据隔离。
- Mock：在嵌入式未接入前提供 SOS、跌倒、设备上线、社区播报等模拟事件。

交付物：

- API 契约文档。
- DTO/实体/迁移设计。
- OpenAPI/Swagger 更新。
- 最小 mock 数据和联调样本。

不要做：

- 不写 App UI。
- 不写后台页面。
- 不碰固件。

### AI-2：家庭 App（用户端）

负责范围：

- 首页看护盘、告警中心、SOS/跌倒紧急弹窗、通知中心。
- 设备列表/详情、设备设置、配网绑定占位流程。
- 家庭成员、声纹录入状态、家属投喂、家庭任务。
- 社区消息查看、播报回执展示。
- 生活服务：陪诊、家政、B 端公司合作服务下单和订单状态。
- 合作医院：资源展示、复诊/随访、陪诊衔接。
- 隐私授权和会员权益展示。

交付物：

- App 页面、路由、状态管理、Repository。
- API 对接或 mock repository。
- 紧急弹窗和通知中心可演示。

不要做：

- 不做社区后台。
- 不做 B 端服务商审核页面。
- 不展示其他家庭或社区全量数据。

### AI-3：社区后台（独立社区门户）

负责范围：

- 社区门户菜单和权限。
- 本社区老人、设备、重点老人标签。
- 社区内容发布、审核、撤回、投放计划。
- 触达回执：已下发、已到达、已播报、App 已查看、失败。
- 告警值班：SOS、跌倒、漏服、离线、长时间无互动。
- 社区项目报表：覆盖率、在线率、告警响应、消息触达率、回访记录。

交付物：

- `community` 门户页面。
- 社区内容和回执管理页面。
- 社区告警处置流程。
- 社区报表导出。

不要做：

- 不做平台全局配置。
- 不做 B 端公司结算。
- 不看跨社区数据。

### AI-4：B 端公司/服务商后台

负责范围：

- 服务商管理：陪诊公司、家政公司、维修公司、助浴/陪护/康复服务商。
- 服务目录：服务类型、价格、区域、时段、人员资质。
- 履约流程：接单、派人、上门、服务中、完成、凭证、评价、投诉。
- 合作医院：协议、科室资源、权益包、转诊/随访配置。
- 企业门户：合同、SLA、对账、结算、发票、服务质量统计。

交付物：

- 服务商后台页面。
- 合作医院配置页面。
- 履约节点和投诉处理页面。
- B 端对账/SLA 基础页面。

不要做：

- 不做用户 App 下单页面。
- 不做社区内容发布。
- 不访问无授权的老人健康和对话数据。

### AI-5：联调、权限、测试与验收

负责范围：

- 统一端侧边界检查：App、社区后台、B 端后台、平台后台分别能看到什么。
- 多租户权限测试：community 不能看其他社区；enterprise 不能看社区全量；App 只能看自己家庭。
- 核心链路联调：社区发通知、SOS/跌倒事件、服务下单履约、医院资源展示。
- mock 数据：至少准备家庭、社区、服务商、医院、设备、告警、内容各一套。
- 验收报告：每条主链路的操作步骤、接口、页面和结果。

交付物：

- 测试用例清单。
- 联调脚本或手工验收步骤。
- 权限矩阵。
- 问题清单和修复建议。

不要做：

- 不主动重构业务代码。
- 不扩大范围到嵌入式固件。

## 3. 可以直接发给 5 个 AI 的任务说明

### 发给 AI-1

你负责后端接口与数据模型。请按 `24-五AI并行开发分工与端侧边界.md` 的 AI-1 范围开发，优先补齐推送 token、设备设置、声纹、家庭任务、社区内容、触达回执、跌倒/SOS 处置、服务商、合作医院接口。所有接口必须带租户/家庭/企业权限边界，先支持 mock 事件联调，不碰 App 和后台 UI。

### 发给 AI-2

你负责家庭 App 用户端。只做用户和家属能看到的功能：看护盘、告警中心、紧急弹窗、通知中心、设备、家庭成员、声纹、投喂、社区消息、生活服务下单、合作医院、隐私授权。不要做社区后台和 B 端后台页面。

### 发给 AI-3

你负责独立社区后台。只做社区/机构管理员使用的门户：本社区老人设备、告警值班、社区内容发布、触达回执、重点老人、回访、项目报表。必须严格限制只能看本社区及下级租户数据。

### 发给 AI-4

你负责 B 端公司/服务商后台。生活服务范围是陪诊、家政，以及与 B 端公司合作的服务内容。请做服务商管理、服务目录、价格区域、履约节点、评价投诉、结算对账、合作医院协议和资源配置。不要做用户 App 页面和社区内容发布。

### 发给 AI-5

你负责联调、权限和验收。请建立 App、社区后台、B 端后台、平台后台的权限矩阵和测试用例，用 mock 数据跑通：社区发通知、SOS/跌倒处置、服务下单履约、合作医院展示。发现跨端边界混乱或越权立即记录问题。

## 4. 生活服务的定义

生活服务不是泛泛的“商城”，当前只按三类做：

1. **陪诊服务**：已有业务基础，优先复用订单、时间线、陪诊员、报告单。
2. **家政/上门服务**：保洁、维修、助浴、理发、陪护、康复、代办代购等，由合作服务商履约。
3. **B 端公司合作服务**：由签约企业/服务商提供，后台管理资质、服务目录、履约、结算和投诉。

用户 App 看到的是“可购买/可预约的服务和订单进度”；B 端公司看到的是“服务履约和结算”；社区后台看到的是“本社区老人服务记录和项目统计”。

## 5. 第一轮并行开发建议

第一轮不要 5 个 AI 都抢同一块。建议这样并行：

- AI-1 先做 API 契约和 mock 数据。
- AI-2 先做 App 告警、通知、服务、社区消息页面。
- AI-3 先做社区内容和社区告警值班台。
- AI-4 先做服务商和合作医院后台。
- AI-5 同步写权限矩阵和验收用例。

第一轮验收目标：

1. 社区后台发布一条通知。
2. 用户 App 能看到通知。
3. 后台能看到下发/到达/查看回执。
4. 用户 App 发起一个陪诊或家政服务订单。
5. B 端服务商后台能接单并更新履约节点。
6. SOS/跌倒 mock 事件能推给 App，并在社区后台完成处置。
