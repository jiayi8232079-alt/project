## 2. 后端运行时分层

| 层 | 作用 | 关键实现 |
|---|---|---|
| **接入** | Nginx + SSL 卸载，反代到 PM2 cluster | 宝塔面板 |
| **HTTP 管道** | 全局拦截器 / 守卫顺序固定 | `app.module.ts` providers |
| **业务模块** | 38 个 NestJS 模块（见 `03`） | `backend/src/modules/*` |
| **横切基础设施** | 多租户 / 审计 / 限流 / 上下文 | `backend/src/common/*` |
| **数据访问** | TypeORM Repository + 实体订阅器 | `backend/src/entities/*` |
| **外部依赖** | MySQL / Redis / COS / 短信 / AI / 涂鸦云 | 各模块 service |

### 2.1 全局管道顺序（重要）

`app.module.ts` 中注册顺序即执行顺序：

1. `RequestContextInterceptor`（ q最先）—— 用 **AsyncLocalStorage** 把当前 user/tenantId 存入请求上下文，供后续所有层（含 TypeORM Subscriber 单例）读取。
2. `AuditInterceptor` —— 所有写操作落 `audit_logs`。
3. `ThrottlerGuard`（APP_GUARD）—— 基于 **Redis 存储**的全局限流（默认 600/min/IP，跨实例共享，Redis 故障 fail-open）。
4. `TenantSubscriber`（普通 provider，构造时 `dataSource.subscribers.push(this)`）—— `beforeInsert` 自动注入 `tenant_id`，防漏写。

## 3. 横切基础设施（common/）

| 能力 | 文件 | 说明 |
|---|---|---|
| **请求上下文** | `common/contexts/request-context.ts` | ALS：`RequestContext.currentUser()` / `currentTenantId()` |
| **多租户基类** | `common/entities/tenant-aware.entity.ts` | `TenantAwareEntity` 带 `tenant_id` + 索引，默认租户兜底 |
| **租户守卫** | `common/guards/tenant.guard.ts` | 按需 `@UseGuards(TenantGuard)`，灰度可控 |
| **跳过租户** | `common/decorators/skip-tenant.decorator.ts` | `@SkipTenant()` 标记 / admin 跨租户 |
| **租户订阅器** | `common/subscribers/tenant.subscriber.ts` | `beforeInsert` 自动注入 tenantId |
| **租户查询助手** | `common/utils/tenant-query.helper.ts` | `applyTenantFilter` / `withTenantWhere` / `applyTenantScope`（层级） |
| **Redis** | `common/redis/redis.module.ts` `redis.service.ts` | 全局 Redis 客户端（ioredis） |
| **限流存储** | `common/throttler/redis-throttler.storage.ts` | Throttler 的 Redis 后端实现 |
| **审计** | `modules/audit/audit.interceptor.ts` | 写操作全量审计 |
| **字段加密** | 见 `backend/docs/column-encryption.md` | `insurance_info` / `id_card` / `phone` 等列级加密 |
| **JWT 缓存** | `modules/auth/strategies/jwt.strategy.ts` | identity 缓存放 Redis（改密即时失效），载荷含 tenantId |

> 这些是「不要丢的好东西」。新写任何模块都应复用它们，而不是另起炉灶。

## 4. 关键数据流

### 4.1 普通业务请求（下单为例）
```
小程序/App → Nginx → JwtAuthGuard(校验+Redis缓存身份) → RequestContext 注入
  → TenantGuard(校验租户) → OrderController → OrderService(applyTenantFilter)
  → TypeORM → MySQL；写操作经 AuditInterceptor 落 audit_logs
```

### 4.2 实时推送（告警为例）
```
设备/雷达 → 涂鸦云 → (规划:Pulsar) → device 模块 recordEvent
  → 跌倒/SOS：alert 模块规则引擎(不经 LLM) → realtime.gateway 推送
  → socket.io(+Redis adapter 多实例互通) → 家属 App/小程序 横幅告警
  → 严重级触发短信/外呼（规则引擎决定）
```

### 4.3 AI 机器人调用（查用药为例）
```
老人语音 → 涂鸦云 ASR → 智能体(DeepSeek) → 决定调工具
  → POST /mcp (JSON-RPC, HMAC 签名 + X-Device-Id)
  → ai-gateway: TuyaSignatureGuard → DeviceContextGuard(deviceId→userId/tenantId/targetId)
  → 工具 execute(越权校验 assertOwnTarget) → 调既有业务 service → 脱敏返回
  → 落 ai_dialog_log + audit_log → 智能体 TTS 朗读
```

详见 [`08-AI能力与MCP网关.md`](./08-AI能力与MCP网关.md)。

## 5. 当前部署形态（单机 PM2）

```
腾讯云 CVM（2C4G ~ 8C16G）
├── 宝塔面板 + Nginx + SSL
├── PM2 cluster（Node × N 进程）
├── MySQL 8.0
└── Redis
        │
        ▼
   腾讯云 COS（独立）
```

- 数据库时区锁定 `+08:00`；生产环境 `synchronize=false`（必须显式 `DB_SYNCHRONIZE=true` 才允许改表，防误删字段）。
- 读写分离：仅当配置 `DB_SLAVE1_HOST` 时启用（向前兼容单库）。
- 部署 / 迁移 / 回滚 SOP 见 [`11-部署与运维.md`](./11-部署与运维.md)。

## 6. 容量与扩展路线（摘要）

| 用户量 | 设备量 | 现架构能否支撑 | 主要改造 |
|---|---|---|---|
| 1 千 | 200 | ✅ 完全够 | 无 |
| 5 千 | 1k | ✅ 够 | 单机多 PM2 |
| 1 万 | 2k | ⚠️ 勉强 | 读写分离 |
| 5 万 | 1w | ❌ 需改造 | Pulsar/bullmq + socket.io adapter（部分已落地） |
| 10 万+ | 5w+ | ❌ | 微服务化 + K8s + 分库分表 |

**演进原则：不重写、不换语言，全部增量改造。**

五阶段演进路线（每阶段都不重写）：

| 阶段 | 用户量 | 目标 | 关键动作 |
|---|---|---|---|
| Phase 0→A | 0-2w | 单机吃满、多进程一致 | Redis 真用 / socket.io Redis Adapter / bullmq / 读写分离 / 老 service 加租户过滤 / 跌倒去抖 + 心跳 cron / AI 余额检查 |
| A→B | 2w-5w | 容器化、可横扩 | Dockerfile / K8s(HPA) / 健康检查 / Prometheus+Grafana / order 拆分 / event_logs 分区归档 |
| B→C | 5w-10w | 消息中间件升级 | Pulsar 替 bullmq / MySQL 主从 / 涂鸦 Pulsar 生产化 / 跨服务事件总线 |
| C→D | 10w-30w | 微服务化 | 拆 device/ai-gateway/billing / RPC 熔断 / Saga 分布式事务 / gRPC |
| D→E | 30w+ | 全微服务 + 跨地域 | PostgreSQL / 分库分表(按 tenantId hash) / 华北华东双活 / 数仓 |

按 ROI 排序的 P0/P1/P2 优化清单见 [`11-部署与运维.md`](./11-部署与运维.md) §7。

> 进展提示：2026-06-02 架构评审列出的 P0「Redis 真用 / socket.io Redis Adapter / bullmq / 读写分离」在当前代码中**已基本落地**（见 `backend/package.json` 依赖与 `app.module.ts`）。剩余重点：老 service 渐进加租户过滤、涂鸦真实接入、容器化与可观测。

## 7. 未来目标架构（10 万+，方向）

按业务域拆微服务：`user / order / medical / device / ai-gateway / billing / alert / realtime / tenant`，
MySQL 主从 + Redis Cluster + Pulsar 事件总线 + K8s（HPA）+ device_event_logs/ai_dialog_logs 分表。
跨服务通信：同步走 REST（后期 gRPC）、异步走 Pulsar topics（`device.events.*` / `alert.created` / `ai.dialog.finished`）、共享态走 Redis Cluster。

## 8. 设计取舍备忘

- **小程序 vs App**：功能重叠高；小程序主拉新、App 主深度（推送/设备/视频）。
- **先 mock 跑通再切真数据**：设备/SDK 不阻塞业务层开发（既定原则）。
- **安全合规先行**：跌倒/SOS 走规则引擎不经 LLM；健康/个人数据脱敏 + PIPL 导出/删除；AI 写操作二次确认。
