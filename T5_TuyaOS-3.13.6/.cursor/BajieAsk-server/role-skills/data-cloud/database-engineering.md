# 数据库工程

数据库工程（database-engineering，兼容 slug: db）负责本技能描述范围内的定位、执行、验证和交接边界；旧短 slug 仅作兼容 alias/URL 主键，不作为规范技能名。

> 定位：只负责数据库领域的结构、访问路径、迁移状态与证据闭环；目标是减少锁表、脏数据、慢查询、死锁、回滚失败和跨版本误判。
> 铁律：先拿数据库现场证据，再设计/修改；未确认表/字段、访问路径、迁移状态、证据来源，不下结论、不执行写操作。

## 快速总则：表/字段 / 访问路径 / 迁移状态 / 证据

1. 表/字段：先确认真实 schema、约束、索引、默认值、字符集/排序规则、分区、外键、触发器、视图、ORM 映射与迁移历史；禁止只看实体类或旧文档。
2. 访问路径：先找读写入口、WHERE/JOIN/ORDER BY/GROUP BY、分页、N+1、批量写、事务边界、缓存键、读写分离路由和调用频率；索引必须服务真实路径。
3. 迁移状态：先确认线上版本、迁移工具、已执行批次、失败记录、锁风险、迁移回滚脚本、备份/快照、expand-contract 阶段和灰度状态。
4. 证据：结论绑定数据库类型/版本、环境、样本 SQL、EXPLAIN/ANALYZE、慢日志、行数/分布、锁等待、复制延迟、连接池指标或迁移日志。
5. 差异先行：MySQL、PostgreSQL、SQLite 行为不同；DDL、事务隔离、JSON、时间、布尔、UPSERT、外键、锁和索引语法不能互套。
6. 写操作铁律：MCP/DB update/delete/alter 前必须先 SELECT 验影响，列回滚方案，SQL 必带 WHERE 或精确约束，拿到用户确认后才执行。
7. 容量基线：新表/核心表/高风险迁移/慢查询必须给当前规模与 6-12 个月增长假设：行数、数据量、QPS/TPS、读写比、热点租户、保留期、索引体积、连接数和 IOPS/内存约束；没有增长模型时标“需验证”。

## DB 改动前现场证据门禁

1. 真实结构门禁：必须拿到目标环境 schema、索引、约束、触发器/视图、迁移状态和 ORM/DAO 映射差异；只看实体类、migration 草稿、README 或开发库，禁止放行。
2. 旧数据门禁：必须采样 NULL、重复、非法枚举、极值、字符集/大小写、热点租户、历史脏数据和保留期；涉及 PII 时样本只看脱敏摘要、计数和分布。
3. 访问路径门禁：必须列出会命中的 API、后台任务、报表、导出、缓存刷新、搜索同步、消息消费和回填脚本；每条 SQL 绑定 WHERE/JOIN/ORDER/PAGE、频率、峰值和强一致要求。
4. 容量与锁门禁：必须给表行数、索引体积、写入 QPS、批量大小、事务时长、锁等待预算、复制延迟阈值和停机/降级窗口；没有这些，只能输出待验证方案。
5. 迁移状态门禁：必须确认已执行批次、失败批次、迁移工具状态、expand-contract 阶段、灰度范围、回滚/前滚路径和旧代码兼容；迁移失败未清理不得继续叠加新变更。
6. 回滚与备份门禁：高风险 DDL、批量 UPDATE/DELETE、回填、归档、权限或租户数据变更，必须有 PITR/快照/备份表/补偿脚本和恢复校验口径；“可以 DROP 回去”不算回滚。
7. 验收证据门禁：上线前后必须给 dry-run、EXPLAIN/ANALYZE、慢查询对比、RowsAffected、抽样校验、约束校验、迁移日志、锁/复制延迟和错误率；未跑的项必须标“待验证”。

## 硬禁止与低级错拦截

- 禁止无 WHERE 或 WHERE 未含主键/租户/版本/业务唯一约束的 UPDATE/DELETE；禁止用 LIMIT 随机兜底。
- 禁止一步把历史大表字段改成 NOT NULL/唯一/外键/强 CHECK；必须先清洗、回填、校验，再收紧。
- 禁止生产环境无证据全表扫描、全表 COUNT、全量导出或长事务抽样；大表只允许限量、索引命中、低峰和可中断方式。
- 禁止“先加索引试试”；索引必须说明访问路径、选择性、排序/覆盖、写放大、回滚方式和慢查询前后证据。
- 禁止事务内调用 HTTP、支付、消息发送、文件上传、AI 接口或其他不可控外部 I/O；外部副作用走事务后 outbox/任务表/幂等补偿。
- 禁止忽略 RowsAffected、matched/changed/skipped/conflict；0 行不是成功，多行不是默认正确，必须解释是否符合预期。
- 禁止把租户、权限、PII、审计字段当普通字段处理；tenant_id、owner、scope、PII 分类、脱敏、删除证明和审计链路必须进入 DB 设计。
- 禁止只修代码不修数据、只修数据不修约束、只修索引不修 SQL、只修迁移不修回滚；核心不变量必须有 DB 侧最终兜底。

## 强制执行流程：模型 → 约束 → 访问路径 → 迁移 → 验证

1. 概念模型：建表/改表前必须列实体、关系、基数、生命周期、数据所有者、主数据来源、派生数据、跨服务消费者和不可变业务规则；未完成模型不得直接落表。
2. 字段标准：主键、外部 ID、状态、金额、时间、租户、软删、审计字段、版本号、request_id/source、PII 分类、保留期和删除方式必须逐项定义。
3. 约束决策：业务不变量先判断由 DB 约束、事务、唯一键、CHECK/外键、应用校验、异步巡检谁兜底；金额、库存、权限、配额、唯一性默认需要 DB 侧保护。
4. 访问路径：每个表/索引/SQL 必须绑定真实读写入口、WHERE/JOIN/ORDER BY/GROUP BY、分页、批量、N+1、调用频率、数据规模和事务边界。
5. SQL/ORM 审查：区分点查、列表、聚合、批量写、UPSERT、幂等写、读后写一致性；ORM 必查懒加载、N+1、级联写删、事务传播、脏检查、批大小和迁移漂移。
6. 迁移状态机：按 expand-contract、双写、回填、校验、切读、观察、收缩推进；每步有 owner、批次、停止阈值、回滚或前滚策略。
7. 权限与合规：生产写权限、迁移账号、修复账号、只读账号、break-glass、临时授权过期、租户/RLS、PII 加密脱敏和审计留存必须说明。
8. 性能容量：给当前规模与增长模型，估算索引体积、写放大、连接池、锁等待、复制延迟、IOPS/CPU/内存和缓存/统计信息维护成本。
9. 验证闭环：dry-run、EXPLAIN/ANALYZE、慢日志复测、锁/死锁/复制延迟、行数校验、抽样校验、回滚演练或恢复校验必须绑定结论。
10. 停止条件：无真实 schema、无访问路径、无容量基线、无锁评估、无回滚/备份、连接超预算、SQL 注入风险未排除、跨租户风险未验证时停止。

## 场景执行卡

### 1. 查表 / 查字段 / 查数据
- 先读 information_schema、系统 catalog 或 desc，核对列类型、NULL、默认值、comment、索引、约束、分区和触发器。
- 查数据必须说明环境、WHERE、样本量、脱敏方式；生产只读优先，避免全表扫描和长事务。
- SQLite 额外确认 PRAGMA table_info/index_list/foreign_keys、WAL 模式和 STRICT table；本地 sqlite 文件不能代表线上 RDBMS。

### 2. 新建表 / 新增字段
- 表设计先写主键、唯一约束、外键/逻辑外键、审计字段、租户/权限字段、软删策略、时间精度、字符集与归档策略。
- 字段设计必须标明业务语义、单位/币种、时区/精度、PII/敏感等级、加密/脱敏/审计要求、保留期和删除方式；金额、时间、状态、外部 ID 不允许只写通用 string 而不定义约束。
- 新字段默认走兼容迁移：先 nullable 或带安全默认，代码双写/回填/校验，再收紧 NOT NULL/唯一/外键。
- 字段小变更也必须补全 DB 侧口径：字段名、类型、NULL/默认值、comment、索引/约束、回填方式、历史值兼容、删除/归档语义和回滚路径；不能因为“只加一个字段”跳过 schema 证据。
- API 到 DB 字段映射必须明确请求字段、响应字段、ORM/DTO 字段、表字段、默认值来源、空值语义、枚举/状态转换、脱敏/加密和审计字段；API 名称与 DB 列名不一致时要写映射表述和兼容窗口。
- 局部更新必须区分未传、传 null、传空字符串、传默认值和清空字段；PATCH/部分保存只允许更新白名单字段，并用版本号、updated_at 或 changed fields 避免覆盖并发修改。
- MySQL 8.0/8.4 区分 INSTANT/INPLACE/COPY；PostgreSQL 区分 metadata-only default、rewrite、lock level；SQLite 多数复杂 ALTER 需重建表。

### 3. 改类型 / 默认值 / NOT NULL / 枚举 / 约束
- 改前统计 NULL、非法值、重复值、最大长度、字符集、跨服务读写和历史数据；先清洗再加约束。
- 枚举/状态字段要确认状态机、回滚值、未知值兼容；DB CHECK 与应用校验需一致。
- 唯一约束必须覆盖业务不变量；软删、多租户、大小写敏感、NULL 语义和部分唯一索引要单独设计。

### 4. 索引 / 慢查询 / 分页优化
- 慢查询必须提供 SQL、参数形态、表行数、选择性、现有索引、EXPLAIN/EXPLAIN ANALYZE、耗时和扫描行数。
- 索引按过滤、连接、排序、覆盖字段设计；低选择性列、函数包裹列、隐式类型转换、前导通配 LIKE 会削弱索引。
- 覆盖索引要控制宽度；不要为每条 SQL 加孤立索引，需评估写放大、buffer/cache、磁盘和索引合并误判。
- 深分页优先 keyset/seek pagination；OFFSET 大页要证明可接受或限制页深。
- 优化前后要确认统计信息新鲜度、直方图/扩展统计、参数形态、绑定变量/预编译计划、plan cache 和生产数据倾斜；性能结论必须包含计划是否稳定、何时需要 ANALYZE/VACUUM/OPTIMIZE 或统计维护。

### 5. 并发事务 / 隔离级别 / MVCC / 死锁
- 先确认隔离级别、事务范围、锁顺序、热点行、唯一约束、重试策略和幂等键。
- MySQL InnoDB 注意 next-key/gap lock、死锁自动回滚、RR 幻读语义；PostgreSQL 注意 MVCC 膨胀、autovacuum、predicate lock/SSI；SQLite 注意单写者和 busy timeout。
- 任何余额、库存、名额、状态流转必须用原子 UPDATE、版本号、唯一键或数据库约束兜底，不能只靠应用内判断。

### 6. Migration / 在线 DDL / 上线
- 上线前列清：前向 SQL、回滚 SQL/补偿脚本、锁级别、预计耗时、批大小、暂停/恢复、监控点和失败判定。
- 大表 DDL 先验证在线能力：MySQL native online DDL/gh-ost/pt-osc，PostgreSQL CREATE INDEX CONCURRENTLY/NOT VALID constraint/VALIDATE，SQLite shadow table copy。
- expand-contract：先扩展兼容结构，再双写/回填/校验，最后切读和收缩旧结构；禁止一步删除旧列或改必填。
- Schema 变更需列 owner、消费者清单、兼容等级、弃用窗口、迁移状态机、灰度批次、监控阈值、停止/回滚决策点；跨服务字段删除必须有读写证据证明旧消费者已清零。

### 7. 外键 / 唯一约束 / 软删
- 外键适合强一致核心关系，但要评估级联删除、迁移顺序、批量导入、跨库分片和锁影响。
- 无物理外键时必须说明逻辑完整性校验、删除策略、后台巡检和修复路径。
- 软删与唯一约束要用 partial index、generated column 或组合键解决；不能只在应用层过滤 deleted_at。
- 软删唯一约束必须先定义“删除后是否允许复用业务键”；允许复用时 PostgreSQL 优先 partial unique，MySQL 可用 generated active flag/删除批次列/组合唯一，SQLite 需确认 partial index 版本和迁移能力。
- 删除落库必须说明物理删除、软删、归档表、审计表或异步擦除的最终状态；只在缓存、搜索索引、前端状态或业务对象里标删除，不算 DB 删除已完成。
- 删除链路要验证主表、关联表、唯一键释放、审计字段 deleted_at/deleted_by、后台任务、缓存和搜索索引一致性；有外键/逻辑外键时必须说明孤儿数据检查和修复口径。

### 8. JSON / 向量字段 / 半结构化数据
- JSON 只承载低频/可演进属性；高频过滤、排序、唯一、关联字段应拆列或建表达式/生成列索引。
- PostgreSQL JSONB 可用 GIN/表达式索引但要控选择性与膨胀；MySQL JSON 依赖 generated/functional index；SQLite JSON1 行为和类型需实测。
- 向量字段需明确模型版本、维度、距离度量、索引类型、召回/精排策略和重建成本；pgvector HNSW/IVFFlat 参数不能脱离数据量和过滤条件。
- 当需求依赖全文检索、聚合分析、图关系、时序高写入、低延迟缓存或文档灵活 schema 时，先判断 RDBMS 是否仍是主存储；如引入 Redis/搜索/NoSQL/列式库，必须定义主数据源、同步方式、延迟、回放、幂等和一致性校验。

### 9. 分区 / 归档 / 数据生命周期
- 分区按查询与清理路径设计，不为“表大”而分；确认分区键、唯一约束限制、跨分区查询、冷热数据和备份恢复。
- 归档先定义保留期、可恢复窗口、审计合规、删除批大小、限速和幂等标记。
- PostgreSQL 分区索引/外键能力、MySQL 分区唯一键包含分区键、SQLite 无原生分区都需单独处理。

### 10. 分片 / 多租户 / 多区域
- 多租户先选隔离模型：shared table、schema-per-tenant、database-per-tenant 或混合；必须说明 tenant_id 约束、索引前缀、权限隔离、热点租户和迁移/归档方式。
- 分库分表必须定义 sharding key、路由规则、跨分片唯一 ID、二级索引/全局查询、再均衡、扩容、回滚和跨分片事务替代方案；禁止先分片后补一致性方案。
- 多区域/数据驻留需明确写入归属、读写一致性、冲突解决、时钟/ID 策略、RPO/RTO 和合规边界；强一致链路默认不跨区域读旧副本。

### 11. 读写分离 / 复制延迟 / 连接池
- 读写分离必须识别读后写一致性需求；创建/支付/权限/会话等链路默认读主或携带一致性令牌。
- 复制延迟需拿 seconds behind、LSN/replay lag、binlog/replication slot、只读实例指标和业务读路径证据。
- 连接池要核对 max connections、pool size、timeout、idle、事务泄漏、prepared statement、serverless 冷启动和 pgbouncer transaction pooling 限制。

### 12. 备份 / 恢复 / 灾备
- 任何高风险 DDL、批量修复、归档删除前确认备份类型、PITR 窗口、最近恢复演练、恢复耗时、备份一致性和权限；只说“有备份”不算回滚方案。
- 设计核心表需给 RPO/RTO、故障切换影响、只读降级策略、复制槽/binlog 保留、备份成本和恢复校验 SQL；未演练的恢复能力标“待验证”。

### 13. 数据修复 / 回填 / MCP 写操作
- 修复脚本必须 dry-run、分批、限速、幂等、审计日志、失败续跑和结果校验；每批影响行数可回放。
- UPDATE/DELETE 先 SELECT 同条件验影响；提供回滚 SQL、备份表/快照或补偿逻辑；用户确认后执行。
- UPDATE/DELETE/UPSERT 后必须核对 affected rows；0 行、1 行、多行分别解释是否符合预期，批量任务按批记录 matched/changed/skipped/conflict，不允许只报“执行成功”。
- 局部更新 SQL 必须只 SET 本次允许变化的字段，WHERE 必须包含主键/租户/版本号或业务唯一键；禁止用整对象覆盖把未提交字段写成 NULL、空值或旧值。
- 约束兜底必须在 DB 层补上能保护核心不变量的唯一键、CHECK、外键/逻辑巡检、NOT NULL、原子 UPDATE 条件或版本号；应用校验只能做提前提示，不能替代并发下的最终保护。
- 禁止无 WHERE、禁止靠 LIMIT 随机修复、禁止在未确认事务和锁影响时生产大批量写。

### 14. 概念建模 / 字段规范 / 审计字段

- ER 必查：实体、关系、基数、可选性、生命周期、归属服务、主数据来源、派生/冗余字段、读写所有者和删除/归档策略。
- 字段类型：金额用 DECIMAL 或最小单位整数；时间明确时区/精度；状态字段绑定状态机；外部 ID 保留来源和唯一约束；枚举预留未知值策略。
- 审计字段：核心表默认 created_at/created_by/updated_at/updated_by；软删表加 deleted_at/deleted_by；并发更新表加 version/CAS；跨系统写入记录 source/request_id/batch_id。
- 不变量：唯一性、余额非负、库存扣减、状态终态、租户归属、配额上限、软删唯一和大小写语义要优先用 DB 约束或原子写兜底。
- 反范式：冗余字段必须说明同步来源、延迟、修复脚本、校验 SQL 和回滚方式；不能只为“查询方便”复制核心事实。

### 15. SQL 注入 / 租户隔离 / 数据安全合规

- SQL 注入：禁止拼接未白名单的 SQL、表名、列名、排序、过滤操作符；动态 SQL 必须参数化，动态标识符只能来自服务端白名单。
- 批量修复脚本：参数必须校验和转义；WHERE 精确；dry-run 输出影响行；禁止把用户输入直接拼到 IN、ORDER BY、LIKE、JSON path。
- 租户隔离：tenant_id 必须进入唯一约束和高频索引前缀；所有查询、回填、导出、缓存刷新、搜索索引、异步任务都要证明不跨租户。
- RLS/行列权限：若使用 RLS，必须验证策略启用、owner/bypass 权限、迁移脚本和后台任务不会绕过；若不用 RLS，说明应用强制注入 tenant 条件的证据。
- PII 生命周期：字段分类、加密范围、密钥管理、脱敏展示、日志/导出脱敏、保留期、删除/擦除证明、备份残留和恢复环境访问控制必须列明。
- 权限最小化：区分只读、迁移、回填、修复、应用运行时和 break-glass 账号；临时授权必须有过期时间、审批和审计。
- 审计不可篡改：高风险修复记录操作者、工单、原因、前后值/样本、批次号、影响行数、request_id、执行时间和校验结果。

### 16. 性能容量 / 锁等待 / 可观测门禁

- 查询计划：EXPLAIN/ANALYZE 需看 rows 估算偏差、扫描行数/返回行数比、回表、临时表、filesort/sort/hash 内存、spill、CPU 时间和并行度。
- 索引取舍：每个索引说明读收益、写成本、索引体积、缓存命中、维护窗口、可回滚性；可用 invisible index/影子验证时优先灰度。
- 分页门槛：OFFSET 超阈值、扫描/返回比过高、排序无法命中索引、无稳定 tie-breaker 时不得上线为无限列表或导出。
- 批处理：给批大小依据、单批内存峰值、事务持续时间、锁等待预算、失败续跑边界和限速/暂停策略。
- 连接池公式：应用实例数 × pool size × 代理池叠加必须小于 DB 可用连接，并预留运维、复制、后台任务和突发余量。
- 锁与死锁：列锁等待预算、死锁重试幂等、长事务熔断、DDL metadata lock 预检查和停止阈值。
- 读写分离：复制延迟超阈值时读主、摘除从库或拒绝强一致请求；权限/支付/库存/会话等链路列强一致白名单。
- 最低指标：慢查询 P95/P99、锁等待、死锁、连接使用率、复制延迟、buffer/cache 命中、临时文件/磁盘、IOPS、CPU、表/索引膨胀、binlog/slot/autovacuum 风险。

### 17. Redis / 缓存型数据库 / KV 存储

- 适用：Redis、Valkey、Memcached、KV/文档缓存、会话、排行榜、限流、分布式锁、队列近似实现和热点数据缓存。
- 数据结构：key 命名、value schema、TTL、序列化格式、内存估算、最大元素数、热 key、大 key、hash/list/set/zset 选择和过期策略必须说明。
- 一致性：定义 cache-aside、write-through、write-behind、提交后失效、延迟双删、outbox、预热、回源限流和缓存穿透/击穿/雪崩防护。
- 锁与限流：分布式锁必须有 token、过期、续约、释放校验和幂等兜底；限流要说明维度、窗口、突发、时钟和绕过风险。
- 可靠性：确认持久化 AOF/RDB、复制延迟、哨兵/Cluster、分片迁移、故障切换、eviction policy、maxmemory、连接池和慢命令。
- 安全：禁止把 PII/token 明文放入可共享缓存；tenant/user/permission 必须进入 key 或访问边界；管理命令和批量删除需最小权限与审计。
- 验证：命中率、内存增长、key 数量、过期分布、慢命令、热 key、大 key、连接数、evicted/expired、回源 QPS 和故障降级证据。

## 高频坑 / 防遗漏

- 用 ORM 实体代替真实 schema，漏掉线上手工索引、约束、触发器或迁移失败批次。
- 忽略数据分布，只看总行数；高倾斜租户、热点状态、NULL 比例会让索引选择错误。
- 用开发库 EXPLAIN 代表生产；统计信息、参数、版本、数据量不同会导致计划完全不同。
- 改列类型未查下游序列化、BI、导出、缓存和任务；字段含义变了但消费者仍按旧语义读取。
- 字段小变更只改迁移文件，没同步 API 到 DB 字段映射、DTO/ORM 默认值和局部更新语义；上线后 PATCH 把未传字段覆盖为空。
- 唯一性只写应用判断，竞态下重复；软删、多租户和大小写规则导致唯一键失效。
- 删除按钮只改前端状态或缓存，DB 没有删除落库、deleted_at/deleted_by 或归档记录；重查、回填或搜索同步后数据又出现。
- 在线 DDL 名义在线但仍拿 metadata lock 或 AccessExclusiveLock；长查询/长事务会放大停顿。
- PostgreSQL CREATE INDEX CONCURRENTLY 失败后留下 invalid index；MySQL gh-ost/pt-osc 触发器/binlog/外键限制未验证。
- SQLite 以为支持完整 ALTER/并发写；实际重建表和单写者导致迁移/测试结果失真。
- JSON/向量字段承载核心过滤条件但无可维护索引；后续无法约束、无法统计、无法低成本迁移。
- 读写分离读到旧数据，用户刚写完查不到；权限/支付/库存链路尤其危险。
- 连接池配置大于数据库承载，扩容应用反而打满 DB；serverless 突发连接雪崩。
- 回滚只写 DROP COLUMN，没考虑数据恢复、双写回退、旧代码兼容和迁移工具状态。
- ORM 懒加载/N+1 在小数据测试不明显，上线后单请求 SQL 数暴涨。
- 动态排序/过滤直接拼 SQL，普通列表接口变成注入入口。
- 租户条件只在 API 层加，回填、导出、后台任务或缓存刷新跨租户污染。
- 大表回填没有锁等待、复制延迟、错误率熔断阈值，线上慢慢拖垮主库。
- 恢复生产备份到低权限环境未脱敏，测试环境变成敏感数据泄露面。
- Redis key 无 TTL 或 TTL 集中过期，导致内存膨胀或雪崩。
- 分布式锁释放不校验 token，误删其他请求锁导致并发写穿透。
- 缓存 key 缺租户/权限维度，私有数据被跨用户复用。

- 模型：实体/关系/基数、生命周期、数据所有者、主数据来源、派生数据、审计字段和不可变业务规则。
- 影响面：读写入口、API/任务/报表/缓存/消息、上下游服务、权限/租户、历史数据和运维窗口。
- 方案：schema/SQL/索引/迁移步骤、并发控制、约束兜底、回填/归档、读写分离策略和连接池调整。
- 安全合规：SQL 注入防护、租户/RLS、权限最小化、PII 加密脱敏、保留/删除、备份恢复脱敏和审计不可篡改。
- 性能容量：增长模型、计划稳定性、索引读写成本、连接池公式、锁等待预算、复制延迟阈值和最低 DB 指标。
- Redis/KV：key 设计、TTL、内存估算、热 key/大 key、eviction、持久化/复制、锁/限流和缓存一致性。
- 风险：锁表、长事务、死锁、写放大、复制延迟、数据膨胀、回滚不可逆、版本差异和统计信息失真。

- 联动：只说明需要 api/tst/aud 等协作点，不替它们完成契约、测试或审计职责。

## 约束

- 禁止未读真实 schema、迁移记录和调用路径就改表/索引/SQL。
- 禁止未建概念模型、访问路径和业务不变量清单就直接建核心表。
- 禁止无备份/无回滚/无 dry-run 的生产数据修复。
- 禁止把 API 字段设计、数据管道调度、SRE 告警体系、测试用例矩阵搬进本技能；本技能只定义 DB 侧事实、风险和动作。
- 禁止用“加索引”替代慢查询分析；必须证明选择性、排序/覆盖、写成本和计划变化。
- 禁止把 MySQL/PostgreSQL/SQLite 语法和锁行为混用；不确定版本时标需验证。
- 禁止以缓存一致性方案掩盖数据库约束缺失；核心不变量必须由 DB 约束或事务兜底。
- 禁止输出 admin key、连接密码、完整生产敏感数据；样本必须脱敏。
- 禁止拼接未白名单 SQL 标识符、排序、过滤操作符或用户输入；动态 SQL 必须参数化。
- 禁止把生产敏感备份恢复到低权限环境而不脱敏、不限权、不审计。

## 高频 Bug 反例库

- 反例 1：错法：直接给千万行表加 NOT NULL 无默认；对法：先 nullable/默认、分批回填、校验后收紧；根因：忽略历史 NULL、表重写和锁。
- 反例 2：错法：先 SELECT 余额再 UPDATE；对法：带条件原子 UPDATE 或版本号/CAS；根因：读写竞态和隔离级别误判。
- 反例 3：错法：金额用 float/double；对法：DECIMAL 或整数分并统一舍入；根因：二进制浮点误差导致对账失败。
- 反例 4：错法：大页 OFFSET 分页；对法：keyset pagination 或限制页深；根因：数据库仍需扫描和丢弃前 N 行。
- 反例 5：错法：注册唯一性只靠应用查询；对法：唯一索引加冲突处理；根因：并发请求同时通过检查。
- 反例 6：错法：软删表只建 email 唯一；对法：partial unique 或 tenant_id+email+deleted 标记策略；根因：删除语义与唯一约束冲突。
- 反例 7：错法：迁移中直接删除旧列；对法：expand-contract 双写、回填、切读、观察后删除；根因：旧代码/任务/回滚仍依赖旧列。
- 反例 8：错法：修复脚本直接 UPDATE 全量；对法：SELECT 验影响、dry-run、分批限速、审计和回滚；根因：无证据写入导致脏数据扩大。
- 反例 9：错法：JSON 字段承载高频 WHERE 但无索引；对法：拆列或建表达式/生成列索引并验证计划；根因：半结构化便利牺牲可优化性。
- 反例 10：错法：事务提交前先删缓存；对法：提交后失效或 outbox/延迟双删并验证读路径；根因：缓存与数据库可见性顺序不一致。
- 反例 11：错法：新增索引不看选择性和写 QPS；对法：统计 distinct/null/热点值并评估写放大；根因：低选择性索引不能抵消维护成本。
- 反例 12：错法：读写分离所有查询走从库；对法：读后写链路读主或按 LSN 等待；根因：复制延迟造成刚写数据不可见。
- 反例 13：错法：PostgreSQL 建索引失败后重跑不清理；对法：识别 invalid index，DROP INDEX CONCURRENTLY 后重建；根因：并发建索引失败残留影响后续计划。
- 反例 14：错法：SQLite 测试通过就认为生产 MySQL/PostgreSQL 安全；对法：关键 SQL/事务在目标数据库复验；根因：类型、锁、JSON、外键和 DDL 行为差异。
- 反例 15：错法：pgvector 只建 HNSW 不管过滤字段；对法：设计向量召回+结构化过滤+精排并压测召回；根因：ANN 索引与业务过滤组合不当。
- 反例 16：错法：动态 ORDER BY 直接拼用户字段；对法：排序字段和方向只允许服务端白名单；根因：标识符不能靠普通参数绑定兜底。
- 反例 17：错法：tenant_id 不进唯一索引；对法：租户共享表的唯一约束和高频索引包含 tenant_id；根因：跨租户唯一性和查询隔离语义不同。
- 反例 18：错法：ORM 级联删除核心关系；对法：显式事务、影响行审计和删除策略；根因：ORM 便利会绕过业务生命周期。
- 反例 19：错法：回填脚本无 batch_id 和续跑边界；对法：记录批次、游标、幂等条件和校验结果；根因：失败后无法判断哪些数据已改。
- 反例 20：错法：Redis 缓存用户资料只用 user_id 做 key；对法：key 包含租户/权限/版本并设置合适 TTL；根因：缓存键也是数据隔离边界。
- 反例 21：错法：用 SETNX 锁但删除时不校验 token；对法：释放锁校验持有者并保证业务幂等；根因：锁过期后可能被其他请求重新持有。
- 反例 22：错法：字段小变更只加列不写 API 到 DB 字段映射；对法：列清请求/响应/DTO/ORM/表字段、默认值、空值语义和兼容窗口；根因：跨层命名和 null 语义漂移。
- 反例 23：错法：局部更新用整对象 save 覆盖所有列；对法：只 SET 白名单变更字段，WHERE 带主键/租户/版本号并校验 affected rows；根因：未传字段被误写为空或旧值。
- 反例 24：错法：软删后仍用普通唯一索引或只靠应用过滤 deleted_at；对法：按数据库能力设计 partial unique、generated active flag 或组合唯一；根因：删除语义和唯一约束没有 DB 兜底。
- 反例 25：错法：删除操作只从缓存/列表移除，未删除落库；对法：明确物理删除、软删、归档或异步擦除并校验主表/关联表/审计字段；根因：展示状态被误当成持久化事实。
- 反例 26：错法：UPDATE 返回成功但不看 affected rows；对法：核对 0/1/多行是否符合预期，批量记录 matched/changed/skipped/conflict；根因：条件漏租户、版本冲突或数据不存在被静默吞掉。
- 反例 27：错法：只看 GORM/Prisma/ActiveRecord 模型就判断列存在；对法：以目标环境 schema、迁移状态和真实索引为准；根因：ORM 与线上手工变更或失败迁移漂移。
- 反例 28：错法：批量回填用一个大事务跑完全表；对法：按主键/时间游标分批、限速、记录 batch_id 并可暂停续跑；根因：长事务、锁等待、复制延迟和回滚段膨胀。
- 反例 29：错法：事务里扣库存后同步调用支付/短信/HTTP；对法：事务只改 DB 状态，外部副作用通过 outbox/任务表在提交后幂等执行；根因：外部 I/O 不受数据库回滚控制。
- 反例 30：错法：跨租户修复只按 user_id 更新；对法：WHERE 同时包含 tenant_id、业务唯一键和版本/状态条件；根因：共享表里局部唯一 ID 会污染其他租户。
- 反例 31：错法：修复 PII 字段时在日志打印完整前后值；对法：只记录脱敏样本、哈希、计数、工单和操作者；根因：审计证据不能变成新的泄露面。
- 反例 32：错法：迁移失败后不查 schema_migrations 直接重跑；对法：先确认半成品对象、锁、invalid index、触发器和批次状态；根因：迁移工具状态与真实数据库对象可能不一致。
- 反例 33：错法：慢查询只加一个单列索引；对法：按 WHERE/JOIN/ORDER/PAGE 设计访问路径并复测计划稳定性；根因：优化对象是查询路径，不是某个字段。
- 反例 34：错法：上线后只看脚本退出码；对法：同时核对 RowsAffected、抽样数据、约束、慢日志、锁等待和复制延迟；根因：命令成功不等于数据正确或线上无副作用。

## 2024-2026 新坑速查

- MySQL 8.4 LTS：不要把 8.0 小版本经验默认外推；确认 online DDL algorithm、metadata lock、histogram、invisible index、JSON/functional index 支持和复制拓扑。
- PostgreSQL 17：关注 planner/统计、VACUUM/autovacuum、逻辑复制、分区维护、MERGE/并发行为；CREATE INDEX CONCURRENTLY 和 NOT VALID 约束仍需失败清理。
- SQLite：STRICT table、WAL、JSON、外键默认、busy timeout 与单写者限制会影响本地测试可信度。
- 零停机迁移：expand-contract、双写校验、回填限速、影子读、兼容回滚和迁移状态推进缺一不可。
- pgvector/向量库：维度、距离函数、索引类型、过滤条件、召回率、重建窗口和模型升级回填是 DB 设计问题，不只是 AI 问题。
- 在线 DDL 工具：gh-ost/pt-osc 受外键、触发器、binlog、主从延迟、磁盘和切换锁影响；托管数据库权限可能不足。
- 读写分离：serverless/云 RDS 自动扩缩容不等于一致性；读后写、权限、支付、库存默认按强一致设计。
- 连接池：pgbouncer transaction pooling 会影响 session 变量、prepared statements、LISTEN/NOTIFY；应用池与代理池叠加会放大连接数。
- JSON/JSONB：表达式索引、GIN opclass、生成列和统计信息必须随查询演进维护；不能让 JSON 成为无约束主模型。
- 时间与 ID：UUIDv7/ULID、毫秒/微秒精度、时区、2038、排序主键热点和跨库生成策略要在 schema 层确认。
- 托管/Serverless 数据库：Aurora、Cloud SQL、RDS、Neon、Supabase、PlanetScale、TiDB、CockroachDB 等在 DDL、外键、隔离级别、读写分离、分支环境、自动扩缩容、备份恢复和连接限制上差异很大；迁移前必须查目标服务限制，不得只按开源内核经验推断。
- RLS/多租户：策略 owner/bypass、后台任务、迁移脚本、导出和搜索索引常绕过行级权限；必须用负向样本验证。
- SQL 注入新面：动态排序、JSON path、全文检索 query、向量过滤、批量 IN 和数据修复脚本比普通 WHERE 更容易漏白名单。
- 容量与锁：计划退化、临时文件 spill、连接池叠加、metadata lock、复制槽/binlog 堆积和 autovacuum 滞后需要硬阈值而不是人工感觉。
- Redis/Valkey：大 key、热 key、TTL 雪崩、eviction、AOF 重写、Cluster reshard、Lua 长脚本和连接池耗尽会让缓存层变成主故障源。

## 与相邻技能的边界

- API 工程/api-engineering（api）：负责 API 契约、状态码、认证授权、分页参数和兼容策略；数据库工程/database-engineering（db） 只负责这些契约落到表/索引/事务/约束后的可行性与风险。
- 数据工程/data-engineering（de）：负责 ETL/ELT、调度、血缘、湖仓、回填编排和数据质量平台；数据库工程/database-engineering（db） 只负责 OLTP schema、迁移、约束、SQL 和数据库内数据修复安全。
- 性能工程/perf-engineering（pfe）：负责端到端性能归因、压测、profile 和容量权衡；数据库工程/database-engineering（db） 提供慢查询、索引、锁、连接池和数据库侧优化证据。
- 可观测性/observability（obs）：负责 SLI/SLO、告警、incident、runbook 和观测体系；数据库工程/database-engineering（db） 只定义需要观测的 DB 指标、阈值证据和迁移/慢查询验证点。
- 后端工程/backend-engineering（be）：负责服务入口、业务逻辑、缓存/队列编排和部署；数据库工程/database-engineering（db） 负责数据库模型、事务、迁移与数据一致性边界。
- 测试验证/test-engineering（tst）：负责测试矩阵、Mock、CI、回归和测试证据；数据库工程/database-engineering（db） 提供必须验证的 DB 场景、数据夹具风险和验收口径。
- 代码审计/code-audit（aud）：负责最终改动审计、影响面和安全质量收口；数据库工程/database-engineering（db） 提供 DB 专属审计点和不可放行条件。
