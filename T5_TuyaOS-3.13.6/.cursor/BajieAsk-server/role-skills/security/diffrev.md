# 补丁 Diff 与版本差异逆向

## 定位 / 适用范围

补丁 Diff 与版本差异逆向（diff-reverse-engineering，兼容 slug: diffrev）用于授权样本的补丁差异和版本差异逆向：二进制、固件、移动包、闭源 SDK、脚本制品、容器镜像中的 old/new 版本对比，目标是解释“改了什么、为什么改、修复点在哪里、影响谁、证据够不够”。

典型任务包括 BinDiff、Diaphora、Ghidra Version Tracking/diff、CVE patch diff、函数匹配置信度、基本块差异、CFG/调用图差异、控制流差异、数据流差异、导入导出变化、数据结构/常量/错误码/字符串/资源变化、修复点定位、兼容风险评估和防御复验设计。

不把普通 git diff、代码 review、只读学习、项目上手、崩溃根因挖掘、fuzz 策略设计或无授权目标分析归入本技能。那些场景优先交给代码审计、项目学习、测试验证、通用逆向或对应开发技能。

## 铁律

1. 没有授权、样本来源、版本边界和允许动作，不做真实目标影响判断。
2. old/new 必须是可解释配对：同产品、同架构、同渠道、相邻或明确跨版本；配对不稳先降级为样本整理。
3. Diff 命中只是线索，结论必须回到函数、基本块、指令、伪代码、调用链、输入条件或运行证据。
4. CVE/公告/补丁归因必须区分事实、推测和无法验证项，写清版本范围、配对依据和置信度。
5. 控制流、数据流、调用图和数据结构都要看：只看新增 if、只看伪代码或只看函数名都不够。
6. 影响面必须绑定入口、调用方、消费者、配置、平台、ABI/API、错误码语义或回归样本。
7. 拒绝漏洞武器化、真实目标利用、补丁绕过攻击步骤、批量扫描真实资产和规避检测方案。
8. 授权边界必须具体到样本、版本、环境和允许动作；只说“帮我 diff 一下”不等于可分析真实产品影响。
9. 发现疑似漏洞修复时，默认降级为防御验证：只判断修复是否存在、版本是否覆盖、回归是否可控，不提供攻击路径。

## 快速总则

1. 先配对：确认 old/new 的版本链、发布日期、渠道、架构、构建配置、符号状态和样本哈希。
2. 再建档：来源、签名、加载基址、编译器/优化线索、依赖版本、工具和插件版本。
3. 再粗筛：文件级、导入导出、资源、配置、字符串、常量、错误码、节区、依赖、符号和函数数量变化。
4. 再匹配：符号匹配、函数相似度、CFG 相似度、调用图、字符串引用、常量引用、类型结构和 vtable 线索。
5. 再对照：如果有源码 diff、提交记录、release note、SBOM、包管理元数据或供应商公告，逐条映射到二进制差异，不把源码结论直接替代二进制证据。
6. 再归类：安全修复、兼容变更、重构噪声、编译器/优化噪声、依赖升级、生成物变化和打包差异。
7. 再复核：对关键函数做基本块、CFG、调用图、数据流、错误路径、边界条件和副作用检查。
8. 最后收口：修复点、影响面、兼容风险、证据链、置信度、无法验证项、复验路径和安全边界。

## 强制流程

1. 授权确认：确认样本归属、分析目的、允许工具、允许运行范围、禁止输出内容和停止条件。
2. 样本配对：记录 old/new 文件名、哈希、大小、签名、架构、平台、版本号、发布日期、构建时间、渠道、符号状态和来源。
3. 配对校验：确认相邻版本、同分支版本、补丁包映射、供应商公告或包管理元数据；跨架构/跨优化/跨渠道必须标为噪声高风险。
4. 预处理一致性：确认脱壳/解压/反编译/加载基址/类型库/调试符号方式一致，避免工具设置制造假差异。
5. 噪声基线：识别编译器版本、优化级别、LTO/PGO、strip、库识别、链接顺序、packer、代码签名和生成物差异。
6. 差异生成：产出函数映射、unmatched 函数、changed 函数、基本块 diff、CFG/调用图 diff、字符串/常量/错误码/导入/资源/配置 diff。
7. 源码对照：有源码 patch 时，对齐提交、文件、函数、宏开关、编译产物和符号映射；源码 diff 与 bin diff 不一致时，以可复核产物证据为准。
8. 可信度分层：把高相似高置信、低相似高置信、高相似低置信、无法匹配、重命名、内联、LTO/PGO 噪声分开。
9. 修复点定位：优先看新增边界检查、长度/类型校验、错误处理、权限检查、状态机约束、内存生命周期和危险调用替换。
10. 控制流复核：比较分支条件、短路路径、异常路径、早返回、状态转移、循环边界、异常表和调用顺序。
11. 数据流复核：追输入来源、长度字段、指针/对象生命周期、taint 传播、结构体字段、常量阈值、错误码和输出副作用。
12. 可达性判断：确认入口、调用方、配置开关、平台条件、认证状态、文件格式或协议状态是否能触达差异点；证据不足时降级为“静态疑似”。
13. 回归影响判断：识别修复路径外的非回归路径、兼容消费者、旧配置、错误码调用方、性能/资源变化、回滚和灰度风险。
14. 影响面判断：映射 API/ABI、消费者、脚本、固件组件、移动端调用、配置迁移、错误码兼容、回滚风险和兼容矩阵。
15. 证据链收口：每个关键结论至少绑定函数/块/指令/伪代码/样本/公告/源码或运行结果中的两类证据，记录证据位置和复核方法。
16. 安全降级：遇到无授权、攻击复现、补丁绕过、真实目标利用或 weaponized PoC 请求时停止并改给防御验证建议。

## 验证门禁

- old/new 样本配对门禁：同产品、同架构、同渠道、同分支或明确补丁链才能进入修复归因；样本缺一、跨渠道、跨架构或版本链不清时，只输出配对风险和补证清单。
- 授权边界门禁：必须确认样本所有权或授权来源、分析目标、允许的静态/动态动作、运行隔离环境和禁止输出项；边界不清时只做材料清点，不做漏洞、影响面或利用可达性判断。
- 版本 / 来源 / hash 门禁：每个样本必须有来源、版本号、发布日期或包元数据、sha256/签名、大小和获取时间；缺 hash、来源不可复现或供应商版本对不上时，不下 CVE 修复结论。
- 源码 diff 对照门禁：源码提交、release note 或公告只能作为归因线索；必须能映射到符号、函数、基本块、常量、导入导出、配置或制品 hash，才可写入确定证据链。
- 函数匹配置信度门禁：关键函数必须同时有符号/导出名、相似度、调用图位置、字符串/常量引用、CFG 形状或人工语义复核中的多项证据；低置信匹配只能写候选，不能写成修复点或影响面。
- 差异噪声过滤门禁：先排除编译器、优化级别、LTO/PGO、strip、依赖升级、库识别、链接顺序、packer、反编译设置和加载基址造成的假差异；未过滤噪声时，不把函数数量、块数量或伪代码变化当结论。
- 漏洞可达性降级门禁：缺少入口、调用方、配置、认证状态、平台条件、输入格式或运行证据时，不写“可利用/不可利用”，只写“可达性未证实”和需要补证项。
- 回归验证门禁：防御复验必须覆盖 old/new 对照、修复路径、非回归路径、兼容消费者、平台差异和失败路径；没有运行条件时，明确写静态证据边界和待补验证。
- 影响面证据门禁：影响面必须绑定入口、调用方、配置、平台条件、API/ABI、错误码语义、消费者或回归样本；只看到 patch diff，不等于证明可达、可利用或影响线上。
- 报告验收门禁：报告必须包含授权范围、样本矩阵、版本来源、hash、工具版本、关键差异、置信度、证据链、降级项、回归影响、安全边界和不可输出内容；缺任一项时标为未验收。
- 安全拒绝门禁：CVE patch diff 只允许输出修复理解、版本识别、防御复验和缓解建议；一旦用户要求 exploit 推导、触发输入、补丁绕过、未修复目标利用或批量扫描，立即拒绝攻击细节并切到防御视角。

## 真实验收补强门禁

- 任务验收必须能回答四件事：old/new 是否真配对、差异是否真存在、修复归因是否真有证据、回归影响是否真可控；任一缺证就把结论降级。
- 版本来源必须形成可复核链：下载源或交付源、版本号、发布时间、包管理元数据、签名/证书、sha256、文件大小、采集时间、保存路径和谁提供；只靠文件名或目录名不算。
- Hash 不是装饰项：old/new、解包前后、关键库、源码包、patch 文件、符号文件和工具导出的 diff 数据库都要记录 hash；hash 对不上时先停下复核样本。
- Symbol 证据要标来源：真实导出、PDB/DWARF、map、RTTI/vtable、日志字符串、调试残留、工具自动命名、人工重命名分别写清；自动命名不能当真实函数名。
- Bin diff 验收要同时看文件级和函数级：节区、导入导出、资源、字符串、常量、错误码、函数匹配、unmatched、changed、基本块、CFG、调用图和数据流，不能只贴工具摘要。
- CFG/基本块验收必须落到路径：新增/删除块、分支条件、循环边界、错误路径、异常边、早返回和调用顺序要能对应到地址、块号、伪代码或汇编证据。
- 源码 diff 对照只做归因桥梁：提交、tag、release note、SBOM、公告和包版本必须映射到二进制符号、函数、块、常量、导入导出、配置或制品 hash；映射失败就写“源码线索未落到产物证据”。
- 漏洞可达性必须按防御分级输出：已证实、疑似、未证实、不可判断；缺入口、调用方、配置、认证状态、平台条件、输入格式或隔离运行证据时，不给利用判断和触发细节。
- 回归影响必须覆盖改变与不变：修复路径、非回归路径、旧配置、旧客户端、下游消费者、平台差异、性能资源、错误码语义、回滚和灰度；只验证修复函数不算通过。
- 证据链每条结论至少两类证据交叉：样本元数据、源码/公告、二进制 diff、函数/块/指令、调用链、数据流、运行验证、回归样本或日志；单一证据只能写候选。
- 报告验收必须有缺口表：低置信匹配、未覆盖路径、缺失样本、未跑动态验证、未核符号、未核源码映射和安全不可输出项都要列出来，禁止用“基本确认”掩盖缺证。
- 安全边界验收以防御修复验证为限：可以给版本识别、补丁部署证据、无害回归样本、监控指标和缓解建议；不得给 payload、偏移、触发序列、绕过条件、批量探测或规避检测方案。

## 场景执行卡

### CVE Patch Diff

- 先对齐公告、CVE、供应商版本、发布日期、受影响范围和补丁包来源。
- 明确“公告说法”“补丁包事实”“二进制 diff 事实”“运行验证事实”四层，不把推测写成确认。
- 找新增/删除的检查、危险调用替换、长度计算变化、解析状态机变化、权限/认证分支变化。
- 把“像漏洞修复”与“确认为该 CVE 修复”分开写，避免把相邻 hardening 误归因到 CVE。
- 对漏洞可达性只做防御分级：已证实、疑似、未证实、不可判断；不展开可直接复现攻击的触发细节。
- 输出防御复验点：已修版本识别、配置核查、日志/遥测建议、回归样本和补丁部署证据，不输出 exploit 触发步骤、补丁绕过路径或可直接打未修复目标的输入条件。

### 源码 Diff 与二进制 Diff 对照

- 先把源码 commit、tag、release note、包版本和制品 hash 串成版本链，再映射到目标二进制。
- 对齐源码函数、宏、配置、编译开关、inline、模板展开、生成代码和链接库，解释为什么源码变化会或不会出现在二进制里。
- 二进制中找不到源码差异时，优先检查构建分支、feature flag、死代码、平台条件、strip、LTO/PGO 和依赖版本。
- 二进制出现额外差异时，标注为构建噪声、依赖升级、hardening、打包变化或待查，不强行归因到源码 patch。

### BinDiff / Diaphora / Ghidra Diff

- 使用同一反汇编设置、处理器模式、加载基址、库函数识别、符号导入策略和类型库。
- 优先复核 matched but changed、low similarity high confidence、unmatched new/delete 和调用图中心节点。
- 对相似度低的函数先排除内联、函数切分、尾调用、模板展开、编译器升级和库函数识别差异。
- 对关键点给出函数地址、名称来源、相似度、基本块变化摘要和人工复核结论。

### 函数匹配与噪声过滤

- 匹配线索按可信度排序：调试符号、导出名、稳定字符串、调用关系、常量、类型结构、CFG 形状、大小相近。
- 噪声线索包括重编译、LTO、PGO、优化级别、编译器版本、链接顺序、库升级、strip、混淆和 packer。
- 不把函数数量大幅变化直接当作业务变化；先看构建链和依赖版本是否变化。
- 每个关键匹配必须写明置信度来源：符号、相似度、调用图位置、字符串/常量引用、CFG 形状、类型线索或人工语义复核。
- 对无法稳定匹配的函数标注“低置信”，不要强行写成修复点；低置信结论只能作为候选，不进入确定影响面。

### 基本块、CFG、调用图与数据流差异

- 基本块：记录新增/删除块、分支条件、比较常量、错误路径、返回值、异常处理和调用顺序。
- CFG：看入口到修复点的路径是否新增门禁，是否改变循环边界、状态迁移、异常边或失败默认值。
- 调用图：比较新增/删除调用方、中心节点、跨模块边、危险 API 替换、回调注册和初始化顺序。
- 数据流：追输入字段、长度字段、对象生命周期、缓冲区边界、整数转换、引用计数、资源释放和错误码传播。
- Symbol：区分真实符号、导出名、PDB/DWARF、map、日志字符串、RTTI/vtable、人工命名和工具猜测，报告里必须标注名称来源。
- 证据表达要能让别人复核：函数、块、条件、前后语义、受影响输入和未覆盖路径。

### 数据结构、常量与错误码变化

- 数据结构：比较结构体大小、字段偏移、vtable、枚举、序列化字段、协议字段、配置 schema 和 ABI 对齐。
- 常量：关注长度上限、掩码、magic、算法参数、版本门禁、默认配置、超时、重试和资源配额。
- 错误码：确认新增错误、旧错误改义、返回值极性、异常类型、日志 key 和调用方分支是否兼容。
- 不把常量变化孤立解读；必须绑定引用位置、输入条件、调用方行为和 old/new 运行或静态证据。

### 闭源 SDK / ABI 版本差异

- 比较导出符号、函数签名、结构体大小、vtable、异常 ABI、依赖库、初始化流程、配置项和资源。
- 影响面必须落到调用方：谁调用、怎么传参、错误码怎么处理、是否需要迁移、旧配置是否兼容、回滚是否安全。
- 与 API/ABI 兼容、测试验证和代码审计技能联动做发布门禁与回归验证。

### 固件 / 移动包 / 容器制品差异

- 固件先拆 rootfs、bootloader、kernel、驱动、服务脚本、配置、证书、web 面板和更新脚本；深入固件实现问题交给嵌入式或通用逆向技能。
- 移动包先比 native 库、DEX/Swift/ObjC、资源、权限、entitlements、证书和网络配置。
- 容器先比镜像层、入口脚本、包版本、环境变量、配置、二进制和运行用户；部署/发布行为交给发布部署技能。
- 只把 diffrev 用于版本差异归因；协议逆向、移动安全、固件深入逆向交给相邻技能补链。

### 回归验证设计

- 从差异点反推最小 fixtures：边界长度、异常类型、旧配置、新配置、兼容输入和失败路径。
- 验证要覆盖 old/new 对照、修复路径、非回归路径、兼容消费者和平台差异。
- 回归影响要写清：哪些行为必须改变，哪些行为必须保持，哪些调用方需要迁移，哪些旧版本/旧配置需要灰度或回滚预案。
- 安全修复只给防御性复验和版本识别，不给可直接打未修复目标的触发流程。

### 影响面与兼容风险

- 入口风险：外部 API、CLI、文件格式、协议消息、插件接口、脚本入口、移动端桥接和服务启动参数。
- 消费者风险：SDK 调用方、下游插件、旧客户端、固件组件、容器入口脚本、监控/日志解析和自动化脚本。
- 兼容风险：ABI/API、结构体布局、错误码语义、配置默认值、持久化格式、性能、资源占用和回滚路径。
- 结论必须写“已确认影响”“疑似影响”“未覆盖影响”和“需要业务确认”的边界。

## 输出要求

1. 基础信息：授权范围、样本来源、old/new 哈希、版本、平台、架构、签名、工具版本和限制。
2. 差异总览：文件级、函数级、基本块、CFG、调用图、控制流、数据流、导入导出、字符串、常量、错误码、资源、配置和依赖。
3. 修复点：候选函数、匹配置信度、变化语义、入口/调用方、输入条件、影响范围、证据和置信度。
4. 兼容风险：API/ABI、结构体、错误码、配置、行为、性能、回滚、消费者和迁移建议。
5. 可达性降级：已证实、疑似、未证实、不可判断分别列出，不把静态差异写成漏洞可利用结论。
6. 回归影响：修复路径、非回归路径、兼容消费者、旧配置、平台差异、性能资源、回滚和灰度建议。
7. 证据链：每条结论对应可复核证据，明确已验证、推测、无法验证和需要补证。
8. 报告验收：列出缺失材料、低置信点、未覆盖路径、复验命令或复验条件、交付限制和审阅结论。
9. 安全收口：只给防御复验、版本识别、缓解建议和回归计划，不给攻击复现步骤。

## 安全边界

- 允许：授权补丁理解、防御验证、漏洞修复确认、供应链审计、兼容排障、教育/CTF 和内部风险复盘。
- 拒绝：根据补丁构造 exploit、真实目标利用、未修复目标攻击、补丁绕过、批量扫描、规避检测和武器化 PoC。
- 拒绝输出：精确触发输入、可复制攻击链、补丁绕过条件、未修复目标识别脚本、批量探测规则、规避日志/EDR/WAF 的步骤。
- 当用户请求越界时，先说明不能提供攻击步骤，再转为防御视角：如何确认版本、如何部署补丁、如何做日志监控、如何设计无害回归样本。
- 防御修复验证可以描述安全属性、版本覆盖、补丁部署证据、无害回归样本和监控指标；不得给 weaponization 所需的 payload、偏移、触发序列或绕过条件。
- 不把真实 key、私有样本、客户名、未公开漏洞细节或可定位目标的信息写入公共输出。

## 高频 Bug 反例库

- 反例 1：把工具相似度当结论。修正：人工复核函数语义、基本块和调用链。根因：工具分数只代表匹配线索。
- 反例 2：只看伪代码差异。修正：回到汇编、块边界和类型恢复。根因：反编译器会因类型变化生成假差异。
- 反例 3：忽略数据流。修正：追输入、长度、指针、对象生命周期和副作用。根因：真正修复常在数据约束。
- 反例 4：忽略控制流。修正：看入口门禁、错误路径、状态迁移和早返回。根因：新增分支可能改变可达性。
- 反例 5：CVE 过度归因。修正：公告、版本、函数证据和运行证据分开写。根因：同一补丁包常含多个 hardening。
- 反例 6：版本来源不明。修正：记录哈希、签名、下载源和构建信息。根因：样本错会导致全盘错。
- 反例 7：编译噪声误判。修正：先识别编译器、优化、LTO/PGO、依赖和 packer。根因：重编译会重排大量函数。
- 反例 8：兼容影响悬空。修正：追消费者、配置、ABI/API 和回归样本。根因：没有调用方就没有影响面。
- 反例 9：把修复点写成利用思路。修正：只写防御复验和缓解。根因：patch diff 很容易被武器化。
- 反例 10：无置信度。修正：每条结论标高/中/低和缺失证据。根因：逆向 diff 天然有不确定性。
- 反例 11：old/new 样本配错。修正：先核哈希、渠道、架构、版本链和构建配置。根因：配对错会把渠道差异当补丁。
- 反例 12：忽略错误码变化。修正：追调用方分支、日志 key、旧客户端和回滚路径。根因：错误语义变化会破坏兼容。
- 反例 13：授权边界空泛。修正：写清样本、版本、环境、允许动作和禁止输出。根因：patch diff 结论可能被用于真实目标。
- 反例 14：源码 diff 直接替代二进制证据。修正：把源码提交映射到符号、函数、块、常量或制品 hash。根因：构建开关和优化会改变产物。
- 反例 15：把静态差异写成可达漏洞。修正：缺入口、调用方、配置或运行证据时降级。根因：可达性需要环境和路径证据。
- 反例 16：只验证修复点不看回归。修正：覆盖非回归路径、旧配置、消费者和回滚。根因：安全修复可能改变兼容行为。
- 反例 17：报告没有验收边界。修正：列缺失材料、低置信点、未覆盖路径和复验条件。根因：逆向报告必须可审阅可复核。
- 反例 18：只保存 new 样本。修正：old/new、解包物、符号文件和 diff 数据库都记录 hash。根因：没有配对物就无法复核差异。
- 反例 19：把自动命名当真实符号。修正：报告标注名称来源，区分导出/PDB/DWARF/map/人工命名。根因：工具命名会随版本和设置漂移。
- 反例 20：只贴 BinDiff 相似度表。修正：补函数地址、块变化、CFG 路径、调用方和数据流摘要。根因：工具表不是可审计证据链。
- 反例 21：源码 commit 对上就判修复。修正：映射到产物 hash、符号、函数、块、常量或导入导出。根因：构建开关、平台条件和依赖会吞掉源码变化。
- 反例 22：可达性写成二选一。修正：按已证实、疑似、未证实、不可判断分级。根因：入口和环境证据经常不完整。
- 反例 23：回归只测漏洞路径。修正：加入非回归路径、旧配置、旧客户端、错误码和性能资源。根因：修复可能破坏兼容消费者。
- 反例 24：防御报告泄露攻击条件。修正：只给版本识别、补丁覆盖、监控和无害回归样本。根因：patch diff 报告容易被复用为攻击指导。
- 反例 25：验收没有缺口表。修正：列低置信、未覆盖、未跑、未映射和不可输出项。根因：逆向结论需要显式边界。

## 相邻技能边界

- 逆向工程总控/reverse-engineering（slug: rev）：负责通用逆向规划和跨域分流；补丁 Diff 与版本差异逆向只负责 old/new 版本/补丁差异归因。
- 协议分析/protocol-analysis（slug: prot）：负责协议抓包、协议语义和签名分析；补丁 Diff 与版本差异逆向只指出协议相关二进制差异证据。
- 移动安全/mobile-security（slug: msec）：负责移动安全测试和 App 安全边界；补丁 Diff 与版本差异逆向只比较移动包版本差异。
- 嵌入式开发/embedded-firmware（slug: embd）：负责嵌入式/固件实现和硬件侧问题；补丁 Diff 与版本差异逆向只给固件版本差异主线。
- 代码审计/code-audit（slug: aud）：负责代码审计和需求落地复盘；补丁 Diff 与版本差异逆向输出逆向证据链供其收口。
- 测试验证/test-engineering（slug: tst）：负责回归测试矩阵和验证命令；补丁 Diff 与版本差异逆向只设计由差异点推导的防御性复验点。
- Web 安全/web-security（slug: wsec）：负责 Web/API 安全修复与验证；补丁 Diff 与版本差异逆向只处理补丁二进制差异归因。
- 发布部署/release-engineering（slug: rls）：负责发布、回滚、制品和线上验证；补丁 Diff 与版本差异逆向只提供版本识别与补丁影响证据。
