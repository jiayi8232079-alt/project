# 逆向报告、证据链与交付收口

## 定位 / 适用范围

逆向报告、证据链与交付收口（reverse-engineering-report，兼容 slug: rev-report）只在逆向分析已经处于“要交付、要归档、要复核、要给修复方接手”的阶段使用。它不替代二进制分析、动态调试、恶意样本分析、崩溃复现、差分分析或协议逆向；它把这些过程产出的观察、日志、截图、偏移、哈希、工具输出和附件整理成防御用途的报告。

适用：

- 授权样本、固件、二进制、移动包、脚本、dump、pcap、崩溃件或恶意样本的逆向分析交付报告。
- 需要建立样本身份、SHA256、版本/构建号、来源、采集时间、派生关系和保管位置。
- 需要记录 OS、架构、模拟器/虚拟机、沙箱、隔离网络、工具链和工具版本，让关键结论可复验。
- 需要把观察分成已验证、推测、无法验证，并为每条发现挂证据编号。
- 需要交付修复方、检测工程、事件响应、合规/法务或客户，并控制敏感信息和可滥用细节。

不适用：

- 只读学习、概念解释、项目上手、README 总结或普通文档润色。
- 代码审计报告、单元测试报告、普通漏洞修复说明或非逆向交付文档。
- 无样本、无证据、无授权、无版本来源，却要求给定性结论或风险评级。
- 攻击性报告、exploit 编写、绕过教程、武器化 PoC、免杀/规避、凭据提取或未授权第三方样本分析。

## 铁律

1. 先确认授权。报告必须写明授权主体、目标范围、样本来源、允许动作、禁止动作、第三方边界、留存策略和发布限制；缺项时写成阻塞项，不补编事实。
2. 样本身份不可省。任何结论都必须能回到样本 ID、SHA256、大小、文件类型、版本/构建号、平台/架构、签名状态、来源渠道、采集时间和派生关系中的可用字段。
3. 证据编号比叙事重要。发现、风险、修复建议和无法验证项都要引用证据编号；截图、日志、偏移、函数、字符串、网络事件、文件事件、崩溃栈和工具输出都必须可追溯。
4. 分级写结论。已验证、交叉验证、高置信推测、低置信推测、证据冲突、无法验证必须分开；不能把工具标签、反编译猜测或单次运行观察写成事实。
5. 复验只给防御最小路径。可以写环境、样本、输入条件、观察点和验收证据；不得输出攻击链、绕过细节、可复用 payload、武器化参数或扩大滥用能力的步骤。
6. 脱敏默认开启。正文、截图、日志、附件名、路径、配置、dump、pcap 和命令摘要都要检查密钥、token、cookie、账号、个人数据、客户数据、内部域名和未授权样本位置。
7. 风险必须可交接。风险评级要说明触发条件、受影响版本、权限/数据影响、利用边界、防御可见性、兼容风险、修复复杂度、回归风险和残余风险。

## 快速总则

- 报告先写元数据：标题、项目/案件编号、报告版本、日期、作者、复核人、授权主体、分发范围、敏感级别、留存/销毁要求。
- 工件先建账：原始样本、工作副本、解包件、dump、日志、pcap、截图、符号、脚本、配置和外部资料分别编号，不用临时文件名代替证据 ID。
- 环境要能重建：记录 OS/内核/运行时、CPU/架构、虚拟化/沙箱、网络隔离、时区、依赖版本、工具名称、工具版本、插件/规则库版本和关键配置。
- 发现按“事实、解释、影响、建议”写：事实只写观察，解释写推断链，影响写边界，建议写修复和复验。
- 证据不够时降级：单点证据、工具孤证、截图孤证、AI 摘要、杀软标签和字符串命中都不能直接支撑高置信结论。
- 报告面向接手者：未参与逆向的人应能按样本清单、证据索引、环境矩阵和复验路径理解关键判断。
- 一次性交付包至少包含：主报告、样本/工件清单、证据索引、附件索引、脱敏记录、复验记录、修复交接清单和开放问题清单；缺任一项要在报告首页列为交付限制。
- 未知字段必须写“未提供/未验证/不适用”和补证动作，不能留空、猜测或用“同上”“最新版”“客户包”等模糊词。

## 交付字段契约

- 授权范围：写明授权主体、资产归属、样本来源、允许动作、禁止动作、时间窗口、第三方边界、数据留存、外发对象和停止条件；缺授权时只做证据保全和缺口清单。
- 样本清单：每个原始样本、派生件、dump、pcap、日志、截图和配置都要有稳定 ID、来源、采集时间、保管位置、脱敏状态和关联结论。
- Hash 与版本：原始样本必须记录 SHA256；可选补 SHA1/MD5 只作辅助。版本、构建号、签名状态、证书、平台/架构和文件大小必须写来源证据，不能用口头描述替代。
- 环境与工具版本：环境 ID 必须覆盖 OS/内核/架构/虚拟化或沙箱/网络隔离/时区；工具 ID 必须覆盖工具名、版本、插件/规则库版本、配置差异和版本固定证据。
- 证据截图/日志：截图要写来源窗口、采集时间、环境 ID、样本 ID、观察点和脱敏状态；日志要写时间范围、时区、采集命令或来源、截取规则、完整日志保管位置和关联发现。
- 发现分级：每条发现必须给事实观察、证据编号、结论级别、影响边界、限制条件、替代解释和降级条件；单点证据默认不能高于“中置信推测”。
- 修复与验收：修复建议必须落到组件/配置/流程/检测规则之一，并写验收证据、回归用例、兼容风险、残余风险和接收团队。
- 交付格式：主报告、样本清单、证据索引、附件索引、复验记录、脱敏记录、修复交接表、开放问题表必须能互相引用同一组 ID。

## 强制流程

1. 授权与边界确认
   - 写清委托方/资产方、样本来源、允许分析动作、禁止动作、第三方边界、生产隔离要求、数据留存策略和外发限制。
   - 授权不完整时，只输出缺口清单、证据保全建议和安全处理建议，不输出确定性技术指控。

2. 样本身份登记
   - 为每个工件分配稳定 ID：S-001 原始样本、D-001 dump、L-001 日志、P-001 pcap、IMG-001 截图等。
   - 记录 SHA256、可选 SHA1/MD5、大小、文件类型、版本/构建号、平台/架构、签名/证书、来源渠道、采集时间、保管位置和派生关系。
   - 版本来源要写明证据：文件元数据、包 manifest、签名证书、内嵌配置、服务端返回、客户声明或外部公告；客户声明只能作为声明，不得当作已验证版本。
   - 同名不同版本、原始样本和派生工件必须分开写；不能只写“最新版”“客户给的包”“那个 dump”。

3. 环境与工具链登记
   - 列出分析主机、虚拟机/模拟器/沙箱、网络状态、隔离策略、系统时区、依赖组件、工具名称、工具版本、插件版本和规则库版本。
   - 任何会影响结果的设置都要写入，例如符号加载、反编译器配置、沙箱网络策略、Hook/调试开关、样本重命名或解密/解包步骤摘要。
   - 工具链记录要能复核版本：命令输出、版本截图、容器镜像 tag/digest、规则库更新时间、插件 commit 或下载来源；无法固定版本时写明漂移风险。

4. 证据链设计
   - 证据编号建议固定前缀：AUTH 授权，S 样本，ENV 环境，T 工具，E 观察，R 复验，A 附件，Q 开放问题。
   - 每条关键发现至少绑定一个主证据；能交叉验证时再绑定运行日志、偏移、截图、工具输出或外部资料。不能交叉验证时写原因。
   - 证据表必须包含来源工件、采集方式、采集时间、工具版本、脱敏状态、访问限制和关联发现。
   - 证据 ID 一旦发布不得复用或改义；废弃证据保留为“作废/替换为 E-xxx”，避免报告、附件和修复单引用错位。
   - 证据编号粒度以“可独立复核的一条观察”为准；一个截图、一个日志片段、一个偏移范围或一次运行结果不要混装多个不相关结论。
   - 截图证据必须能回答“谁在什么环境看到了什么”：包含环境 ID、样本 ID、窗口/工具名、采集时间、关键区域说明和脱敏状态。
   - 日志证据必须能回答“从哪里截取到哪里”：包含日志来源、时间范围、时区、筛选条件、截断说明、完整件位置和敏感字段处理。

5. 发现与结论分级
   - 每条发现包含标题、受影响样本/版本、事实观察、证据编号、复验条件、影响、置信度、限制条件、修复建议和复验方式。
   - 推荐标签：已交叉验证、已验证、高置信推测、中置信推测、低置信推测、证据冲突、无法验证。
   - 置信度口径：已交叉验证=两类以上独立证据支持；已验证=同一环境可复现且证据完整；高置信推测=证据强但缺一个关键复验条件；中/低置信推测=证据有限或替代解释较多；证据冲突=证据间不一致；无法验证=缺样本、环境、权限或触发条件。
   - “无法验证”不是失败，要写阻塞原因、已尝试方法、可能解释、临时处置和下一步补证。
   - 无证据结论必须删除或降级为开放问题；禁止用“显然”“应该”“大概率”“行业常识”替代证据编号。
   - 结论降级要显式写触发条件：缺授权、缺原始样本、缺 hash、缺复验环境、工具孤证、日志截断、截图孤证、样本版本不一致、替代解释未排除或证据冲突。
   - 风险标题不得超过证据能支持的边界；不确定版本范围写成“已验证版本 / 未验证版本 / 待补证版本”，不能扩写为全部版本。

6. 风险、兼容与修复交接
   - 风险说明要包含触发条件、受影响版本/平台、权限或数据影响、可利用性限制、防御可见性、误报风险和优先级依据。
   - 修复交接要写受影响组件、建议修复方向、兼容风险、回归用例、验收门槛、残余风险、负责人/团队和建议时间线。
   - 恶意样本或攻击相关内容只写防御 IOC、行为摘要、检测建议、处置流程和影响边界，不写攻击扩展路径。
   - 修复单必须能落到工程任务：组件/模块、入口条件、失败现象、建议方向、禁止破坏的兼容契约、回归数据、验收证据和回滚/缓解建议。

7. 复验边界与去武器化
   - 复验路径只保留防御最小闭环：样本 ID、环境 ID、工具 ID、输入条件、观察点、预期证据、失败降级和验收标准。
   - 去武器化处理要把攻击链、绕过参数、可复用 payload、投递路径、规避细节和扩展步骤改写成高层触发条件、检测点、隔离建议或修复验证点。
   - 若复验必须依赖敏感输入，正文只写编号、哈希、掩码摘要和受控附件位置；不得把秘密、第三方位置或可滥用命令直接放进报告。
   - 复验不可重建时，必须写明缺失资源、已尝试动作、失败证据、替代验证、结论降级和补证 owner。

8. 脱敏与安全发布审查
   - 对正文、截图、日志、附件、文件名、路径、命令摘要、pcap、dump 和配置做敏感信息检查。
   - 必须保留的敏感证据转为哈希、编号、局部掩码、摘要化描述或受控附件；正文不直贴秘密。
   - 外发版要写清删除了什么、掩码了什么、哪些附件受控、哪些内容不可公开。
   - 外发前执行发布判定：接收方是否在授权范围内、附件是否最小化、样本位置是否隐藏、攻击步骤是否抽象化、敏感字段是否脱敏、受控附件是否有访问期限和审批人。
   - 对外版本不得包含可直接复用的 exploit、payload、绕过参数、免杀/规避细节、完整凭据、完整内部路径、真实样本下载位置或第三方未授权信息。

## 场景执行卡

### 逆向最终报告

- 必填：授权范围、样本清单、环境矩阵、工具链版本、发现列表、证据索引、风险评级、修复建议、复验路径和开放问题。
- 写法：先结论摘要，再证据索引；先已验证事实，再推测和限制；先受影响范围，再修复优先级。
- 禁止：为增强说服力编造复现率、扩大影响版本、删除反证或把“疑似”改成“已确认”。

### 样本身份与哈希/版本报告

- 必填：样本 ID、SHA256、大小、类型、版本/构建号、平台/架构、签名状态、来源、采集时间、原始/派生关系。
- 写法：同名文件按哈希区分；解压、解密、dump、patch、符号化、重打包后的工件必须标明来自哪个原始样本。
- 禁止：只写路径、截图或文件名；把客户口头版本号当作已验证版本；混用多个样本的结论。

### 证据链与附件索引

- 必填：证据 ID、来源工件、采集方式、采集时间、工具版本、脱敏状态、访问限制、关联发现、附件编号。
- 写法：正文引用证据编号，附件承载细节；敏感附件标注受控访问和保留期限。
- 禁止：截图没有来源；日志没有时间和环境；附件含未脱敏凭据、客户数据或可直接滥用样本位置。

### 截图、日志与复验记录

- 必填：截图/日志 ID、环境 ID、样本 ID、工具 ID、采集时间、时区、观察点、脱敏状态、完整件位置、截断原因和关联发现。
- 写法：截图用于证明可见状态，日志用于证明时间线或事件；两者不能互相替代。正文只摘关键片段，完整件进受控附件。
- 禁止：只贴图不写来源；只贴日志不写时间范围；用 AI 摘要替代原始证据；把含秘密的完整日志外发。

### 可复现步骤与结论分级

- 必填：前置条件、环境 ID、样本 ID、输入条件、观察点、预期证据、失败模式、置信度依据。
- 写法：描述防御验证所需的最小动作和观察点；攻击参数、绕过细节和武器化 payload 改写为高层条件。
- 禁止：让读者依赖作者本机状态；省略工具版本；把未复现但合理的判断写成已复现。
- 交付格式：步骤编号、使用的样本/环境/工具 ID、只读或隔离动作、预期日志/截图/哈希/网络事件、失败时如何降级结论。

### 风险、兼容影响和修复交接

- 必填：受影响版本/平台、触发条件、影响类别、严重性依据、兼容风险、修复方向、回归测试、验收标准、残余风险。
- 写法：风险评级绑定证据和假设；修复建议要能变成工程任务；检测建议面向日志、规则、遥测和隔离。
- 禁止：只写“高危”；只给逆向细节不给修复入口；建议破坏兼容却不提示发布风险。

### 脱敏版外发报告

- 必填：分发对象、脱敏规则、保留字段、移除字段、受控附件、不可公开项、复核人。
- 写法：用哈希、编号、掩码、截断和范围描述替代秘密；保留足够证据让授权接收方复核。
- 禁止：公开 token、私钥、完整 cookie、个人数据、客户数据、内部主机名、真实可获取样本位置或攻击流程。

### 修复交接包

- 必填：发现 ID、证据 ID、受影响组件、版本范围、触发条件、用户/系统影响、兼容约束、建议修复方向、验收证据、回归用例、残余风险、负责人或接收团队。
- 写法：把逆向术语翻译成工程可执行项；保留证据引用，删除攻击性细节；明确哪些判断仍需产品、法务、检测或平台团队确认。
- 禁止：只给反汇编/反编译片段不给业务入口；只说“修复校验”不给验收门槛；把不确定版本范围写成全量影响。

### 交付收口验收

- 必填：交付物版本、交付对象、授权引用、样本清单、证据索引、附件索引、脱敏记录、复验记录、修复交接表、开放问题和签收状态。
- 写法：验收清单按“可复核、可修复、可外发、可留存”四类组织；每个未满足项写阻塞等级、owner、补证动作和截止时间。
- 禁止：只给主报告不附索引；只写“已脱敏”不写规则；只写“建议修复”不写验收证据。

## 验证门禁

提交前逐项检查：

- 授权主体、范围、样本来源、允许动作、禁止动作、留存策略、停止条件和发布限制已记录，或列为阻塞缺口。
- 每个关键样本/工件都有稳定 ID、SHA256 和派生关系；同名不同版本没有混用。
- 环境矩阵包含 OS/运行时/架构/隔离方式/工具版本/插件或规则库版本等影响复验的字段。
- 每条关键发现都有证据编号；单证据结论已降级并说明限制。
- 已验证、推测、无法验证、证据冲突和开放问题分区清楚。
- 报告中每个“确认/存在/导致/影响/可复现/修复后通过”都有证据编号支撑；没有证据编号的断言已删除、降级或转为开放问题。
- 风险评级包含触发条件、受影响范围、影响类型、限制条件、兼容影响和修复/缓解建议。
- 复验路径足以防御验证，但不含 exploit、绕过、武器化 payload、免杀规避或滥用步骤。
- 正文、截图、日志、附件、路径和文件名完成敏感信息检查和脱敏说明。
- 修复交接包含受影响组件、建议方向、验收门槛、回归建议、残余风险和责任边界。
- 外发版、内部版、受控附件的差异已登记；分发对象、审批人、访问期限和不可公开项已写清。
- 截图和日志证据均标注来源、环境、时间、截断/完整件位置、脱敏状态和关联发现。
- 复验步骤只包含防御最小动作、观察点和验收证据；可滥用细节已抽象化或转为受控附件。
- 交付包能从任一发现追到样本、hash、环境、工具版本、截图/日志、修复建议和验收标准。
- 反例库已覆盖授权缺失、样本混用、截图孤证、日志截断、结论拔高、复验武器化、修复不可验收和外发泄露。

## 真实验收门禁

报告只有同时满足以下条件，才能写成“可交付/已验收”：

- 授权可验收：有 AUTH 证据编号，覆盖主体、资产、时间窗、允许动作、禁止动作、第三方边界、交付对象、保留期限和停止条件；缺任一关键项时交付状态只能是“受限交付”或“阻塞”。
- 样本可验收：每个进入结论的样本都有 S ID、SHA256、大小、类型、版本/构建号、平台/架构、来源、采集时间、保管位置和派生关系；缺 hash 或版本来源时不得进入“已验证”。
- 环境可验收：每条可复验发现都能对应 ENV/T ID，包含 OS/内核/架构、隔离方式、网络状态、时区、工具名、工具版本、插件/规则库版本、关键配置和版本固定证据。
- 证据可验收：截图、日志、pcap、dump、偏移、函数、字符串和工具输出都有 E/A ID，写明采集时间、采集方式、完整件位置、截断规则、脱敏状态和关联发现。
- 发现可验收：每条发现都有事实观察、证据编号、结论级别、影响边界、替代解释、降级条件、修复建议和验收证据；没有证据编号的风险结论必须删除或转开放问题。
- 复验可验收：复验步骤只包含防御最小动作、样本/环境/工具 ID、输入条件、观察点、预期证据、失败降级和验收标准；不得包含可复用攻击参数、绕过细节或 payload。
- 修复可验收：建议必须能落到组件、配置、流程、检测规则或运营处置，并给出回归用例、兼容风险、残余风险、owner 或接收团队。
- 发布可验收：外发版和内部版差异已登记，受控附件有访问期限和审批人，正文和附件不含密钥、凭据、个人数据、客户数据、未授权样本位置或武器化细节。

验收结论按最低项决定：任一门禁为阻塞，整体不得写“完成”；任一关键证据为单点证据，相关结论最高只能写“中置信推测”；任一版本或样本混用，相关影响范围必须拆分重写。

## 审阅清单

- 授权审阅：授权主体、资产归属、第三方边界、外发对象和禁止动作是否被正文、附件和复验步骤共同遵守。
- 样本审阅：所有发现引用的样本 ID 是否都存在于样本清单；hash、版本、来源、派生关系是否一致；同名不同 hash 是否分开。
- 环境审阅：报告中的“复现/验证/未复现”是否都能追到环境和工具版本；工具版本漂移、规则库更新和配置差异是否说明。
- 证据审阅：每条事实性断言是否有证据编号；截图是否有环境、时间和脱敏状态；日志是否有时区、范围、截断规则和完整件位置。
- 分级审阅：已验证、推测、无法验证和证据冲突是否分区；标题、摘要和风险等级是否没有超过证据边界。
- 安全审阅：复验路径、附件名、命令摘要和截图是否已去武器化；是否没有 exploit、绕过、免杀、持久化、凭据提取或真实样本下载位置。
- 修复审阅：修复建议是否有工程入口、验收门槛、回归用例、兼容风险和残余风险；是否避免只写“加强校验/升级版本/增加检测”。
- 交付审阅：主报告、样本清单、证据索引、附件索引、复验记录、脱敏记录、修复交接表和开放问题表是否能互相按同一组 ID 跳转。

## 输出要求

推荐报告结构：

1. 报告元数据：标题、编号、版本、日期、作者/复核人、授权主体、分发范围、敏感级别、留存策略。
2. 执行摘要：分析目标、核心结论、风险概览、受影响范围、建议优先级、无法验证项。
3. 授权与范围：样本来源、允许动作、禁止动作、第三方边界、环境限制、停止条件、发布边界。
4. 样本与工件清单：ID、SHA256、大小、类型、版本、平台/架构、签名、来源、采集时间、派生关系。
5. 环境与工具链：环境矩阵、隔离方式、工具/插件/规则库版本、关键配置差异。
6. 发现详情：发现 ID、标题、受影响样本/版本、事实观察、证据编号、复验条件、结论分级、风险、兼容影响、限制条件、建议。
7. 证据与附件索引：证据编号、附件编号、来源、脱敏状态、访问限制、关联发现。
8. 修复与复验：修复方向、验证门槛、回归建议、检测/监控建议、残余风险、交接对象。
9. 脱敏与发布说明：移除/掩码内容、受控附件、不可公开项、外发版本差异。
10. 开放问题：无法验证项、阻塞原因、证据冲突、下一步补证动作、相邻技能路由。

表格最低字段：

- 样本清单：样本 ID、SHA256、大小、类型、版本、平台/架构、签名、来源、采集时间、保管位置、派生关系、脱敏状态。
- 环境工具矩阵：环境 ID、OS/内核/架构、隔离方式、网络状态、时区、工具 ID、工具版本、插件/规则库版本、关键配置、版本证据。
- 发现表：发现 ID、标题、受影响样本/版本、事实观察、证据 ID、结论级别、影响、限制、修复建议、验收证据。
- 证据索引：证据 ID、证据类型、来源工件、采集方式、采集时间、工具版本、截图/日志位置、脱敏状态、访问限制、关联发现。
- 修复交接表：发现 ID、组件/团队、建议方向、兼容风险、回归用例、验收门槛、残余风险、owner、状态。

语言要求：

- 使用“观察到”“复现于”“证据 E-xx 支持”“推断为”“无法验证”“需要补证”这类可审计表达。
- 避免“必然可利用”“影响全部版本”“确认后门”等没有证据边界的绝对化措辞。
- 风险、建议和复验都面向防御、修复、检测、合规和交付，不面向攻击扩展。

## 安全边界

允许：

- 授权范围内的防御逆向报告、证据整理、风险评估、兼容影响说明、修复交接和复验计划。
- 对敏感信息做哈希、编号、掩码、摘要化、截断、访问控制和外发差异说明。
- 描述防御检测点、IOC 摘要、修复方向、受影响范围、隔离建议、日志留存和回归验证。

拒绝：

- 编写或完善 exploit、武器化 PoC、绕过步骤、免杀/规避、持久化、凭据提取、盗版绕过或可直接滥用 payload。
- 公开密钥、凭据、token、cookie、个人数据、客户数据、完整敏感 dump、未授权样本位置或第三方未授权信息。
- 对无授权第三方系统、应用、账号、设备、固件、样本或生产环境做结论性报告。
- 为营销、施压、索赔或夸大影响而改写证据、拔高风险、删除限制条件或隐瞒反证。

安全替代：越界时改为输出授权补充清单、证据保全清单、脱敏摘要、防御检测建议、修复验证计划或负责任披露框架。

## 反例库

1. 反例：报告写“确认存在后门”，但没有样本哈希、版本、环境和证据编号。对法：先补样本 ID/SHA256/版本和支撑证据；证据不足时降级为推测。
2. 反例：把反编译器伪代码截图当作唯一证据。对法：补运行观测、偏移/函数、日志、交叉工具结果或文档佐证，并说明工具限制。
3. 反例：复验步骤包含 payload、绕过参数和完整利用链。对法：保留防御最小触发条件和观察点，移除武器化细节。
4. 反例：附件原样保留客户 token、cookie、内部域名和用户数据。对法：掩码、哈希、截断或转入受控附件，并写明脱敏规则。
5. 反例：两个同名样本混用同一个结论。对法：按 SHA256、版本和来源分开，逐条标明受影响范围。
6. 反例：只写“高危”，不写触发条件、影响面和限制。对法：说明触发路径、受影响版本、权限/数据影响、防御可见性和修复优先级。
7. 反例：为了交付完整，把“未复现”改成“已确认”。对法：保留无法验证项、阻塞原因、已尝试方法和下一步补证建议。
8. 反例：报告只写逆向过程，工程团队无法修复。对法：补受影响组件、修复方向、验收标准、回归用例和兼容风险。
9. 反例：恶意样本报告详细描述投递扩展和规避检测。对法：只写行为摘要、IOC、防御检测、处置建议和影响边界。
10. 反例：删除反证和工具限制以提高风险级别。对法：保留证据冲突、替代解释、限制条件和置信度下降原因。
11. 反例：授权只写“客户同意”，没有主体、资产、动作、时间窗和外发对象。对法：补 AUTH 证据；补不齐则停止定性，只交缺口和保全建议。
12. 反例：样本表只写文件名，没有 SHA256、大小、版本和来源。对法：按 S-xxx 建账；缺 hash 的结论不得进入已验证区。
13. 反例：截图看似证明风险，但没有环境、工具版本和采集时间。对法：补 IMG/E 证据元数据；无法补时降级为辅助证据。
14. 反例：日志只贴三行，不说明截断规则和完整件位置。对法：写时间范围、过滤条件、完整日志编号和脱敏状态。
15. 反例：复验步骤可被直接改造成攻击流程。对法：删除参数化滥用细节，仅保留样本/环境/观察点和防御验收证据。
16. 反例：修复建议写“加强校验”，验收无法判断。对法：写组件、入口条件、预期拒绝/日志/检测结果、回归用例和残余风险。
17. 反例：摘要写“全部版本受影响”，正文只验证一个样本版本。对法：摘要改成“已验证版本受影响，其他版本待补证”，并列出版本矩阵。
18. 反例：把沙箱工具标签当作恶意结论。对法：只写工具观察，补行为日志、文件/网络事件或人工复核；未补前降级为推测。
19. 反例：复验命令保留绕过参数和完整 payload。对法：替换为受控附件编号、高层触发条件和防御观察点。
20. 反例：报告附件索引写“见压缩包”，没有文件 hash、脱敏状态和访问控制。对法：每个附件分配 A ID，记录 SHA256、来源、用途、敏感级别、保留期限和审批人。
21. 反例：客户口头说是生产版本，报告写成已验证版本。对法：客户声明只能进来源说明；版本结论必须引用文件元数据、包 manifest、签名、服务端返回或发布公告。
22. 反例：日志时间线跨时区但未说明时区和主机时间。对法：记录环境时区、主机时间校准、日志原始时间和统一时间轴转换方式。
23. 反例：外发版删除限制条件，只保留高危结论。对法：外发版必须保留影响边界、无法验证项、证据冲突和降级原因。
24. 反例：修复建议包含逆向得到的敏感内部细节。对法：交给修复方的正文只保留组件、入口条件、预期行为和验收证据；敏感细节进入受控附件。

## 自检清单

- [ ] frontmatter 中 name 为 canonical `reverse-engineering-report`，description 明确是授权防御逆向报告交付；兼容 slug 为 `rev-report`，自检不得要求 name 等于短 slug。
- [ ] 章节包含定位 / 适用范围、铁律、快速总则、强制流程、场景执行卡、验证门禁、输出要求、安全边界、反例库、自检清单、相邻技能边界。
- [ ] 行数少于 500，且没有 fenced code block。
- [ ] 样本身份、hash/版本/来源、环境工具链、可复现步骤、证据编号、附件索引均有明确要求。
- [ ] 已验证/推测/无法验证、风险/兼容影响、修复交接、脱敏和安全发布边界均有门禁。
- [ ] 授权范围、证据截图/日志、复现边界、结论降级、去武器化、验收清单和交付格式均有明确字段。
- [ ] 未输出攻击步骤、敏感数据、可复用恶意细节或未授权样本信息。
- [ ] manifest triggers 足够窄，anti_triggers 覆盖只读学习、普通文档、代码审计报告、无证据结论和攻击性报告。

## 相邻技能边界

- 逆向工程总控（reverse-engineering，slug: rev）：负责逆向任务总控、授权门禁、样本接收和子技能路由；rev-report 只负责证据化报告和交付收口。
- 二进制逆向（binary-reverse-engineering，slug: binrev）/ 移动逆向（mobile-reverse-engineering，slug: mrev）/ 固件逆向（firmware-reverse-engineering，slug: fwrev）/ Windows 逆向（windows-reverse-engineering，slug: winrev）/ Linux 逆向（linux-reverse-engineering，slug: linuxrev）/ macOS 逆向（macos-reverse-engineering，slug: macrev）/ 脚本与字节码逆向（script-bytecode-reverse-engineering，slug: scriptrev）/ Web 逆向（web-reverse-engineering，slug: webrev）：负责具体载体和平台的逆向分析；rev-report 汇总其证据、环境差异和修复交接。
- 恶意样本逆向（malware-reverse-engineering，slug: malrev）：负责恶意样本行为、IOC、检测和处置分析；rev-report 只做防御交付，不扩展攻击流程。
- 崩溃逆向（crash-reverse-engineering，slug: crashrev）/ 逆向模糊测试（fuzz-reverse-engineering，slug: fuzzrev）/ 差分逆向（differential-reverse-engineering，slug: diffrev）/ 壳与加固逆向（packer-reverse-engineering，slug: packrev）：负责崩溃、模糊测试、版本差分和壳/混淆补证；rev-report 汇总影响、复验、残余风险和附件索引。
- 逆向安全实验室（reverse-engineering-lab，slug: revlab）/ 逆向自动化与批量证据流水线（reverse-engineering-automation，slug: revauto）：负责实验环境和自动化分析流水线；rev-report 引用其环境、日志和工具版本，不把流水线输出当作无需复核的事实。
