# Wechat Pay实战排障版

定位：把微信支付问题收敛为“商户主体正确、接口契约正确、账务状态正确、证据闭环充分”。本技能只管微信支付领域口径与排障卡，不替代 API、DB、后端实现、安全专项、测试或审计。

## 快速总则：商户 / 接口 / 账务 / 证据

1. 商户先定：确认直连、服务商、平台收付通、跨境或特约商户；核 mchid、appid、openid、sub_mchid、sub_appid、sp_mchid、sp_appid 的归属证据。
2. 接口先定：确认 API V3 或 v2 遗留、支付产品 JSAPI/小程序/Native/App/H5/付款码、签名算法 RSA/SM2、证书序列号、APIv3 Key、notify_url 和商户平台配置。
3. 账务先定：支付、关单、退款、分账、分账回退、转账、账单对账都按独立状态机处理；同步响应只是受理证据，不是最终账务事实。
4. 证据先定：每个结论必须绑定请求时间、mchid/appid、out_trade_no、transaction_id、out_refund_no、serial、timestamp / 时间戳、nonce、错误码、回调 headers/body 摘要、解密结果、查单和对账证据。
5. 回调铁律：先验签，再解密，再校验商户、appid、金额分、单号、状态，再幂等原子更新，最后快速 2xx；业务重活异步做。
6. 金额铁律：全链路用整数金额分；优惠、退款、分账、手续费、跨币种换算必须有舍入规则和对账兜底。
7. 安全铁律：私钥、APIv3 Key、平台证书、Authorization、openid、手机号、证件号、银行卡、回调明文默认敏感，日志只留摘要、serial、尾号或 hash。
8. 变更铁律：改商户、证书、密钥、回调域名、订单号、金额、状态机、分账比例、对账规则前，先查调用方、消费方、配置、任务、账务和告警。

## 场景执行卡

### 1. 接入选型与商户平台配置
- 适用：新接支付、直连改服务商、加小程序/公众号/App/H5、开分账、开退款、开转账、迁移 API V3。
- 输入证据：商户号类型、主体、appid 绑定、openid 来源、产品权限、回调域名、支付目录/H5 域名、App 包名签名、小程序 appid、商户平台截图或接口证据。
- 必做：列清资金主体、用户身份主体、接口调用主体；服务商必须区分 sp 与 sub 参数；配置缺口不靠代码绕过。
- 验证：商户平台权限、产品开通、证书/APIv3 Key、域名白名单、测试商户与正式商户差异。

### 2. API V3 下单与客户端调起
- 适用：JSAPI/小程序支付、Native 二维码、App 支付、H5 支付、付款码支付。
- 输入证据：本地订单、金额分、商品描述、notify_url、out_trade_no、payer.openid、scene_info、Authorization 摘要、微信响应。
- 必做：服务端生成下单签名和调起签名；out_trade_no 全局唯一且重试复用；客户端只拿调起参数，不拿密钥。
- 验证：首次下单、同单重试、超时重试、用户取消、支付后查单、关单后重建、旧客户端兼容。

### 3. 签名、验签、平台证书与 APIv3 Key
- 适用：401、验签失败、解密失败、平台证书下载失败、证书轮换、国密 SM2 环境。
- 输入证据：HTTP method、path+query、原始 body、timestamp、nonce、商户 serial、Wechatpay-Serial、平台证书有效期、算法 RSA/SM2。
- 必做：私钥只用于商户请求签名；平台证书按 serial 验回调签名；APIv3 Key 只用于 AES-GCM 解密；轮换期新旧证书和新旧 key 要有兼容窗口。
- 验证：伪造回调失败、合法回调通过、旧 serial 可验、新 serial 可验、错误 key 解密失败、时间偏差告警。

### 4. 回调通知、主动查单与补单
- 适用：支付成功未发货、重复通知、通知延迟、回调被拦、状态乱序、补单任务。
- 输入证据：回调 headers/body 摘要、验签结果、resource 解密、transaction_id、trade_state、本地状态、查单结果、trace_id。
- 必做：先落回调事件或审计日志；按 out_trade_no/transaction_id 幂等；终态不回退；发货、积分、短信、分账触发放异步且可重放。
- 验证：重复回调、乱序回调、伪造回调、回调丢失后查单、查单 NOTPAY/USERPAYING/SUCCESS/CLOSED 分支。

### 5. 退款、关单与异常资金状态
- 适用：全额退款、部分退款、多次退款、退款异常、未支付关单、超时自动关单。
- 输入证据：原支付金额分、累计已退金额分、out_refund_no、refund_id、refund_status、close 状态、退款回调、账单。
- 必做：退款单独落库；本次退款 + 历史成功/处理中退款不得超过原支付金额；退款受理后以回调/查单/对账定终态；关单不能影响已支付订单。
- 验证：重复退款、并发退款、退款 PROCESSING/SUCCESS/CLOSED/ABNORMAL、已支付关单失败、关单后支付回调乱序。

### 6. 分账、分账回退与完结
- 适用：服务商抽佣、平台分润、接收方管理、分账回退、完结分账、投诉冻结。
- 输入证据：profit_sharing 标记、接收方类型与账号、比例/金额、合规材料、分账单号、return_no、finish 证据。
- 必做：下单时声明可分账；接收方先注册并校验；分账、回退、完结分别建状态；完结释放剩余冻结资金；投诉/风控冻结不得强行完结。
- 验证：不可分账订单、比例超限、接收方不存在、重复分账、回退失败、完结后再分账失败。

### 7. 账单下载、账实对账与差异闭环
- 适用：日终对账、交易账单、资金账单、退款账、分账账、手续费差异、人工补单。
- 输入证据：账单日期、账单类型、下载凭证、解密/签名校验、微信侧状态、本地订单/退款/分账状态、差异规则。
- 必做：逐笔比对微信、本地订单、退款、分账、资金入账和手续费；差异单分“微信有本地无、本地有微信无、金额不一致、状态不一致、手续费差异、人工处理”。
- 验证：账单下载失败、解析失败、重复账单、跨日订单、退款跨日、分账跨日、补单后差异关闭。

### 8. 服务商、子商户、跨境、转账与 v2 遗留
- 适用：服务商进件、特约商户、平台收付通、跨境支付、商家转账、v2 现金红包或老接口。
- 输入证据：sp/sub 参数、主体协议、appid 绑定、币种、限额、转账风控、v2/v3 密钥和证书隔离。
- 必做：v2 XML/签名/证书与 v3 JSON/Authorization/平台证书隔离；转账不是退款替代；跨境补币种、报关、结算与合规材料。
- 验证：sp/sub 错配、子商户权限缺失、openid 归属错、限额触发、转账失败重试、v2/v3 回调并存。

## 高频坑 / 防遗漏

- 商户：mchid/appid/openid/sp/sub 归属、产品权限、商户平台绑定、支付域名、notify_url、测试/正式环境。
- 接口：API V3 签名串、path+query、原始 body、Authorization serial、timestamp、nonce、RSA/SM2 算法、HTTP 状态与微信错误码。
- 客户端：JSAPI/小程序调起签名、Native code_url 有效期、H5 Referer/scene_info、App appid/包名/签名、前端 success 不可信。
- 回调：Wechatpay-* headers、平台证书 serial、AES-GCM 解密、幂等、金额分、终态不回退、快速 2xx、异步重活。
- 账务：out_trade_no、transaction_id、out_refund_no、refund_id、分账单号、关单、退款、分账、转账、账单对账。
- 安全：私钥/APIv3 Key/Authorization/openid/手机号/证件号/银行卡/回调明文脱敏；禁止把密钥下发前端或 App。
- 运维：证书/key 轮换、时钟偏差、DNS/HTTPS、回调防火墙、灰度双版本、补偿任务、告警、人工差异处理。

## 约束

- 不凭记忆改支付链路；官方文档、商户平台现网配置和接口实测证据优先。
- 不把同步下单、退款、分账、转账受理包装成最终成功。
- 不把客户端支付结果、跳转结果或前端 success 作为订单成功依据。
- 不在前端、App、小程序保存商户私钥、APIv3 Key、平台证书或完整 Authorization。
- 不用 float/double/元驱动支付、退款、分账、对账；金额口径必须可审计。
- 不在未验签、未解密、未核金额和商户主体时更新业务状态。
- 不替相邻技能设计 API、DB、后端代码、安全复现、测试矩阵或发布流程。

## 高频 Bug 反例库

- 反例 1：API V3 签名串错。错法：用格式化 JSON、漏 query、timestamp/nonce 与头不一致。对法：用实际 method、path+query、timestamp、nonce、原始 body 签名并记录摘要。根因：V3 签名绑定请求原文。
- 反例 2：商户主体错配。错法：直连参数混进服务商 sp/sub，或正式 appid 配测试 mchid。对法：按资金主体和调用主体列 mchid/appid/sp/sub 证据。根因：资金、应用和用户身份三条绑定链不同。
- 反例 3：openid 归属错。错法：公众号 openid 拿去小程序 JSAPI 支付，或用 unionid 当 openid。对法：使用当前支付 appid 下 openid。根因：支付识别用户只认 appid 维度 openid。
- 反例 4：JSAPI/小程序调起二次签名错。错法：前端自己拼 paySign 或 package 少 prepay_id= 前缀。对法：服务端生成 appId/timeStamp/nonceStr/package/signType/paySign。根因：下单签名与调起签名是两段流程。
- 反例 5：Native 二维码复用。错法：商品页长期缓存 code_url。对法：code_url 绑定订单和有效期，超时关单后刷新。根因：code_url 是订单级入口。
- 反例 6：H5 只看后端成功。错法：忽略 H5 域名、Referer、scene_info、IP 和浏览器风控。对法：核商户平台 H5 配置和真实唤起环境。根因：H5 支付受场景和风控强约束。
- 反例 7：App appid/包名签名不一致。错法：后端用公众号 appid，下游 App 用移动应用 appid 调起。对法：用开放平台移动应用 appid 并核包名、应用签名、商户绑定。根因：App 调起依赖客户端应用身份。
- 反例 8：APIv3 Key 当签名密钥。错法：用 APIv3 Key 做 RSA 签名或用私钥解密 resource。对法：商户私钥签名，APIv3 Key 做 AES-GCM 解密。根因：签名验签和报文解密材料不同。
- 反例 9：平台证书轮换漏旧 serial。错法：下载新平台证书后删除旧证书。对法：按 Wechatpay-Serial 选择证书，新旧并存到通知窗口结束。根因：轮换期间不同通知可能使用不同 serial。
- 反例 10：回调不验签不幂等。错法：收到 SUCCESS 就发货，重复通知重复加权益。对法：验签、解密、核商户/金额/单号后按唯一键原子更新。根因：公网回调可伪造、重放和乱序。
- 反例 11：前端 success 改订单成功。错法：wx.requestPayment 或 App SDK success 后直接置已支付。对法：前端只提示处理中，服务端以回调或查单 SUCCESS 为准。根因：客户端结果不可信。
- 反例 12：退款受理当到账。错法：退款接口 200 后立即通知用户退款成功。对法：以退款回调、查单和对账确认 SUCCESS/CLOSED/ABNORMAL。根因：退款是异步资金流程。
- 反例 13：并发退款超额。错法：两个退款请求各自 SELECT 后都通过金额校验。对法：退款单唯一键、事务/锁或原子累计约束。根因：资金扣减不能只靠应用层读后判断。
- 反例 14：分账忘 profit_sharing。错法：支付成功后才发现订单不可分账。对法：下单时声明 profit_sharing=true 并先注册接收方。根因：可分账能力在交易创建时确定。
- 反例 15：分账受理当成功。错法：分账请求返回受理就结算佣金。对法：查分账结果/回调落终态，再完结或回退。根因：分账有冻结、接收方和风控状态。
- 反例 16：关单与支付回调乱序。错法：关单成功后无条件把订单置关闭，覆盖已支付回调。对法：状态机终态保护，关单前后主动查单。根因：外部通知和本地操作存在时序竞争。
- 反例 17：金额用元或 float。错法：优惠后用 19.9*100 转分，退款/分账差 1 分。对法：整数分或 Decimal 明确舍入。根因：二进制浮点不适合资金。
- 反例 18：只对交易账不对资金账。错法：订单 SUCCESS 就认为账平。对法：交易账、资金账、退款、分账、手续费逐笔核对。根因：交易成功不等于资金结算一致。
- 反例 19：服务商子商户账务混淆。错法：用服务商 mchid 查子商户订单或对账。对法：按 sub_mchid/sub_appid 维度查单、退款、分账和账单。根因：服务商只是调用主体，不一定是资金主体。
- 反例 20：排障日志泄密。错法：打印完整 Authorization、APIv3 Key、openid、回调明文、证件号。对法：只留 serial、错误码、hash、尾号和 trace_id。根因：支付日志会进入多系统，泄露面大。

## 2024-2026 新坑速查

- RSA/SM2 并存：接口签名、平台证书、SDK 能力和商户类型要一致，不能把 RSA 示例直接套到国密链路。
- 平台证书 serial 轮换：回调验签必须按 Wechatpay-Serial 命中证书，缓存单证书会在轮换期随机失败。
- APIv3 Key 轮换：新旧 key 兼容窗口要覆盖平台证书下载、回调解密和历史通知重放。
- 服务商/子商户扩张：sp_appid、sub_appid、payer.openid、sub_mchid 口径错会表现为调起失败、分账失败或账单错位。
- 小程序隐私与正式版差异：体验版支付通过不代表正式版商户、域名、隐私声明、基础库和回调链路一致。
- H5/浏览器风控：Referer、IP、域名、WebView、跳转方式和投诉风险会影响唤起，后端 200 不能代表可支付。
- App 包名签名和 SDK 版本：开放平台绑定、包名、应用签名、客户端 SDK 版本任一错都可能调起失败。
- 投诉/风控合规：高投诉、异常交易、分账接收方材料不全会触发冻结、限额、分账失败或交易拦截。
- 关单/退款/回调乱序：用户支付、商户关单、退款申请、微信通知可能交叉到达，状态机必须终态保护。
- 账单对账精细化：交易账、资金账、退款、分账、手续费、跨日订单和人工处理必须拆差异类型。
- AI/自动化排障风险：禁止把密钥、完整回调明文、openid、证件号粘贴到外部 AI 或公共日志。

## 与相邻技能的边界

- wechat-pay：负责微信支付领域事实、商户/接口/账务/证据、场景卡、反例和排障闭环。
- api-design：负责支付相关 API 路由、请求响应、错误码、鉴权、幂等 Header、Webhook 契约和兼容策略。
- db-design：负责订单、支付单、退款单、分账单、对账差异表、唯一索引、事务、状态机和迁移回滚。
- backend-engineering：负责服务端 SDK 封装、配置/密钥装载、任务调度、队列、超时重试、日志、告警和部署运行证据。
- web-security：负责授权范围内的回调入口安全、日志脱敏、密钥泄露、CSRF/CORS/SSRF/越权等专项安全验证。
- wechat-miniprogram：负责小程序 wx.requestPayment、登录/openid、基础库、真机/体验版/正式版、隐私与提审差异。
- test-engineering：负责支付正常/边界/异常/权限/并发/重复/乱序/伪造回调/对账差异的验证矩阵和证据分级。
- release-engineering：负责证书/APIv3 Key 轮换、回调域名、商户配置、灰度、回滚、冒烟和监控发布清单。
- code-audit：负责改动后的最终需求对账、影响面、证据缺口、风险分级和是否允许收口。
