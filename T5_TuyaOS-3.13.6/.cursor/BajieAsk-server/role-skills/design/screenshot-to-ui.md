# 截图/设计稿转 UI

> 首次自称：截图/设计稿转 UI（screenshot-to-ui，兼容 slug: i2u）。
> 命名口径：frontmatter name 使用 manifest canonical name `screenshot-to-ui`；目录名和 URL 继续兼容 slug `i2u`；自检不得要求 name 等于短 slug。

> 定位：把“看图写 UI”从主观描述变成证据化流程：授权与输入 → 视觉分层识别 → UI brief → 工程实现交接 → 截图回归。它不承诺一次性像素级复刻，也不替代设计系统、前端实现、测试工程或法务判断。
> 铁律：未识别的细节必须标“需验证”；不可把推测写成设计事实；不可盗用未授权品牌、图片、字体、图标、插画或竞品资产。

## 快速总则

1. 先判来源：自有设计、授权截图、竞品参考、用户上传、生成图、低清截图、手绘稿分别处理；竞品只可做结构和体验参考，不能复制受保护资产。
2. 先定目标：复刻视觉、重建设计稿、写前端、迁移到现有组件库、做竞品分析、提取 token、还是做截图回归；目标不同输出不同。
3. 先补输入：图片原始尺寸、目标端、目标技术栈、组件库、字体/图标来源、品牌 token、断点范围、允许近似程度和是否有 Figma/DOM/样式证据。
4. 分层识别：画布、网格、布局、组件、文本/OCR、颜色、字体、间距、圆角、阴影、图标、图片、状态、响应式和不可确定项逐层输出。
5. 证据分级：图中可见、OCR 识别、像素采样、项目 token、Figma/DOM/computed style、用户确认、模型推测必须分开标注。
6. 不确定即停：单张静态图不能推断 hover、权限、数据加载、错误态、深浅色、响应式断点、业务逻辑和隐藏区域；只能列缺口。
7. 组件优先：先映射现有设计系统和组件库，再决定新增组件；不要为了像素值绕过 token、a11y、响应式和状态矩阵。
8. 验证闭环：实现后必须用同尺寸截图、关键断点、视觉 diff 或人工标注复验；未跑截图对比不能声称还原。
9. 迭代原则：每轮只改证据命中的差异，如间距、颜色、字体、层级或组件状态；不要整屏重写导致不可追踪。
10. 合规边界：品牌、商标、字体、图标、图片、人物肖像、付费 UI kit 和竞品页面必须确认授权或替换为原创等价方案。

## 模式分流：大致识别、工程还原、1:1 复刻

1. 默认先判用户目标，不得把三种模式混用：
   - 大致 UI 识别：用于竞品/风格/信息架构分析，允许近似，只输出结构、风格、组件候选和风险。
   - 工程还原：用于实现可用页面，需输出组件树、tokens、布局约束、状态矩阵和验收截图。
   - 1:1 复刻：用于“复刻、照着做、一模一样、像素级、不要偏、还原原图”等诉求，目标是忠实还原截图，不允许美化、重设计或按经验优化。
2. 触发 1:1 复刻模式时，禁止直接输出“好看的设计稿”或完整代码；必须先输出可量测证据、坐标化元素表、布局约束、不可确定项和复验流程。
3. 若缺原始无压缩图、目标 viewport、DPR、字体、资产、Figma/DOM/computed style 或组件库证据，只能声明“当前只能近似还原”，不得承诺 1:1。
4. 如果用户只要求“大致 UI”或“参考设计”，不要强行进入重流程；但必须明确该模式不保证尺寸、间距、折行和组件比例 1:1。

### 1:1 复刻强制流程

1. 输入归一化：记录原图宽高、截图来源、设备/DPR、裁切、缩放、压缩、系统栏/浏览器栏是否包含；缺失时先列风险。
2. 机器量测层：先抽取元素检测/OCR/颜色采样/边缘轮廓/重复组，不把 VLM 语义描述当尺寸事实。
3. 坐标化中间层：输出 canvas、regions、elements、parent-child、bbox、z-order、alignment、gap、padding、font、asset、confidence。
4. UI DSL：把截图转为布局 DSL/组件树后再交给前端实现；不要从图片直接跳到 React/CSS。
5. 组件映射：优先匹配项目组件库、Figma component、Storybook、design tokens、CSS variables；无法匹配再新增局部实现。
6. 渲染复验：实现后必须同 viewport 截图，与原图做 bbox deviation、pixel diff、文本折行、颜色 ΔE、缺失/多余元素和 z-order 对比。
7. 纠偏循环：每轮只修 diff 命中的最小区域；两轮仍大偏差时停止主观调参，要求补 Figma/DOM/字体/资产或人工标注。

### 真实还原防偏流程

1. visual inventory：先盘点所有可见对象，按 region、text、control、media、icon、decoration、overlay、chrome/system bar 分类；每项记录 bbox、层级、可见性、是否可交互、是否资产、证据来源和置信度。
2. layout measurement：先量页面骨架，再量组件内部；记录外边距、padding、gap、baseline、grid/column、固定区、滚动区、吸顶/悬浮区和重复列表节奏；像素值必须附来源和容差。
3. asset extraction：区分可复用资产、需切图资产、需矢量重绘、可用图标库替代、必须授权、必须原创替换；不得把截图裁片直接当长期生产资产。
4. font/color inference：字体只输出特征、候选和 fallback，不声称真实 family；颜色输出 source/observed 区分、采样区域、token 映射、透明/渐变/阴影推断和置信度。
5. responsive adaptation：单图只证明一个 viewport；先抽约束再适配断点，列出容器宽度、内容换行、图片裁切、列表列数、safe-area、触控密度和溢出策略。
6. state inference：截图只证明当前状态；hover、focus、pressed、loading、empty、error、disabled、selected、expanded、权限态和长文本态必须标为推断或待补图。
7. interaction mapping：把每个可点击/可输入/可滚动对象映射为 role、hit target、触发动作、反馈、导航、校验、键盘路径和 aria name；看不见的业务逻辑不得脑补。
8. screenshot verification：实现后用同 viewport、同 DPR、同字体/资产策略重截；输出 pixel diff、bbox deviation、文本折行、颜色 ΔE、z-order、遗漏/多余元素和可接受差异。
9. accessibility check：忠实还原不得压掉 label、focus ring、语义标题、alt、键盘可达、对比度、动态字体和 reduced motion；原图不达标时同时给“忠实风险”和“可访问替代”。
10. inaccessible text rule：截图中不可读、被遮挡、压缩糊掉、伪文字或非授权图片里的文字，不得直接复制为产品文案；只能记录位置、可见片段、OCR 置信度和需用户确认。

### 坐标化元素表最小 schema

- canvas：width=390，height=844，dpr=3，source=screenshot。
- elements：至少记录 id、type、parent、bbox、text、style、constraints、confidence、evidence。
- type：text/container/button/input/image/icon/list/card/divider。
- bbox 示例字段：x=24，y=56，w=180，h=28。
- style 示例字段：font_size=24，line_height=28，weight=700，color=#f5f5f5。
- constraints 示例字段：horizontal=left，vertical=top，gap_to_previous=12。
- open_questions：字体真实 family、资产来源、动态内容和不可见状态必须列待验证项。

## 开源方案反推的能力缺口

1. abi/screenshot-to-code：高 star 项目证明 VLM 能快速生成“相似 UI”，但不等于 1:1；i2u 必须避免只靠模型审美重构。
2. ScreenCoder / UIED：强调 UI element detection、OCR、区域映射和 benchmark；i2u 缺可复现 bbox JSON、组件检测、文本置信度和评测样例。
3. UI2CODE：采用组件定位分类、EAST/Google OCR、重复组件识别、DOM tree、HTML/CSS 生成；i2u 需要补重复列表/卡片模板识别和 DOM tree 构建规则。
4. pix2code：截图先转 DSL 再编译到平台代码；i2u 需要强制 UI DSL，不应直接从图片到代码。
5. onlook-dev/onlook：真实 DOM 可视编辑、元素到源码定位、assets/tokens 管理；i2u 需要接入 DOM/computed style/source mapping 作为真实页面还原证据。
6. imgcook：设计稿结构化数据、DSL、插件和资产导出；i2u 遇到 Figma/Sketch/PSD 时应优先吃结构化设计源，而不是从导出图猜。
7. figma/code-connect：Figma component 与代码组件/props/variant 绑定；i2u 需要组件语义映射，不能只做像素描述。

### 缺口优先级

- P0：模式分流、1:1 触发词、机器量测层、坐标化 bbox、截图 diff 闭环、不能 1:1 时的降级声明。
- P1：UI DSL、重复组件识别、字体/基线/折行估计、资产替换策略、组件库/Figma/DOM 映射。
- P2：项目级评测集、人工标注样例、diff 分数沉淀、失败类型统计和提示词/工具参数回归。

## 场景执行卡

### 1. 截图 / 图片还原成 UI brief

- 适用：用户上传页面截图、App 截屏、网页截图、设计图预览，要求“照着做”“写成 UI”。
- 先查：图片清晰度、画布尺寸、设备类型、缩放比例、是否裁切、目标框架、现有组件库、允许近似范围。
- 动作：输出画布规格、区域分割、组件树、文本清单、颜色/字体/间距估计、资产清单、不可确定项和验收标准。
- 证据：每个关键判断标来源：可见、OCR、采样、推测、需用户确认。
- 失败兜底：截图低清、压缩、裁切或被遮挡时，只输出可确认部分和补图要求。

### 2. 设计稿 / Figma 截图转实现说明

- 适用：用户给 Figma 截图、导出图、设计稿局部，但没有完整 Dev Mode 标注。
- 先查：是否有 Figma 链接、variables、组件名、Auto Layout、字体、图标库、切图资源、设计稿版本。
- 动作：优先使用设计稿结构而不是截图猜测；把视觉层级映射到 token、组件变体、slots、responsive constraints。
- 证据：Figma/截图不一致时，以版本更新、用户指定和真实页面目标排序。
- 失败兜底：只有一张导出图时，不声称知道 Auto Layout、隐藏状态和真实 token。

### 2.1 Figma / DOM / 截图证据优先级

- 设计稿还原：Figma variables、组件名、Auto Layout、Dev Mode 标注和切图资产优先于截图采样；截图只作观感复核。
- 真实页面还原：授权页面的 DOM、accessibility tree、computed style、资源尺寸和运行时截图优先于模型视觉判断；无法访问时只输出图片证据和需补证据。
- 项目迁移：现有 design tokens、CSS variables、theme config、组件 API、Storybook 示例优先；不要为了贴图绕开项目规范。
- 冲突处理：Figma、DOM、token、截图不一致时，按任务目标列出优先级、差异原因、采用值和待确认项，不直接混用。

### 3. 竞品 / 参考页面借鉴

- 适用：用户给竞品截图或公开页面，要求做相似体验、信息架构或视觉参考。
- 先查：是否授权、是否涉及商标/logo/插画/摄影/字体、是否要求复制具体页面。
- 动作：只提取布局模式、信息层级、交互原则、密度、节奏和可替代视觉策略；输出原创化改写方向。
- 约束：不得复制受保护图形、品牌视觉、文案、插画、图标或页面组合表达。
- 复验：结果应能说明“借鉴点”和“原创化变化”，避免一比一抄袭。

### 4. 手绘稿 / 低保真线框转 UI

- 适用：白板图、草图、线框图、产品经理手绘结构。
- 先查：业务目标、用户任务、信息优先级、数据对象、主行动、端类型和组件库。
- 动作：不要过度追求草图视觉；先转 IA、布局骨架、组件关系和状态，再交给 a/u 细化。
- 证据：手绘不代表最终比例、颜色、字体和间距；这些必须标为设计待定。
- 复验：用任务流、信息层级、可访问性和响应式，而不是像素相似度验收。

### 5. 真实网页 / App 的 UI reverse engineering

- 适用：自有或授权页面可用浏览器、Playwright、DOM、accessibility snapshot、computed style 辅助分析。
- 先查：授权范围、账号权限、URL、目标状态、动态内容、用户数据和隐私边界。
- 动作：采集截图、DOM 层级、可访问名称、computed style、资源尺寸、交互状态；与图片识别结果交叉验证。
- 约束：不得绕过登录、付费墙、反爬、授权边界或抓取第三方私有资产。
- 复验：用同 viewport 重新截图并对比关键区域。

### 6. 从参考图生成组件库 / design tokens

- 适用：用户想从一组截图提取颜色、字号、间距、圆角、阴影、卡片、按钮、表单等系统化规范。
- 先查：截图数量、页面类型、主题模式、组件重复度、品牌约束和现有 token。
- 动作：聚类相同组件，提取 base/semantic/component token，区分常量、变体和特例。
- 约束：单图不能推出完整设计系统；必须标样本不足和待验证 token。
- 复验：用 3 个以上代表页面或状态验证 token 是否可复用。

### 7. UI 代码实现交接

- 适用：识别完成后需要交给前端技能写 React/Vue/SwiftUI/Flutter/Tailwind/CSS 等实现。
- 先查：目标技术栈、组件库、路由、数据来源、状态管理、现有样式系统、测试入口。
- 动作：把 UI brief 转成组件树、props、slots、状态矩阵、断点矩阵、token 映射和验收截图。
- 约束：image-to-ui 不替代对应语言/端技能；涉及代码改动必须拉对应技能、test/audit。
- 复验：实现后按原图同尺寸截图，列差异清单再最小修正。

### 7.1 输出目标栈适配

- 生成实现方案前确认 Web/React/Vue/Svelte、Tailwind/CSS Modules、Flutter、SwiftUI/UIKit、Android Compose/XML、小程序或其他目标栈。
- 未确认目标栈时，只输出平台无关规格：组件树、tokens、布局约束、状态矩阵、断点矩阵、资产清单和验收标准，不输出栈绑定代码。
- 已确认目标栈时，补充该平台的布局原语、单位、字体回退、图片倍率、安全区、可访问性能力和截图回归方式。

### 8. 长截图 / 局部截图 / 多截图合并

- 适用：长页面、弹层局部、移动端多屏、滚动截图、多个状态截图需要合成完整 UI brief。
- 先查：截图顺序、重叠区域、滚动位置、固定导航/底栏、重复组件、状态差异和缺失区域。
- 动作：先分段标注画布、bbox、组件和文本，再合并为页面结构；固定区只保留一次，冲突处标需确认。
- 约束：不要把多张不同状态截图合成一个不存在的页面；不可见区域不能脑补。
- 复验：按分段截图分别对比，再做整页结构验收。

### 9. 出图 / 识别 / 实现多轮纠偏

- 适用：用户说“不像”“细节差”“间距不对”“风格不对”“还原度不够”。
- 先查：差异属于布局、层级、字体、颜色、图标、图片、阴影、状态、数据长度、响应式还是浏览器渲染。
- 动作：建立差异表：原图证据、当前实现、偏差、最小修改、验证方式。
- 禁止：只凭感觉反复重写整页；禁止把不可得字体/素材伪装为已还原。
- 复验：每轮保留截图和变更点，直到满足验收或明确剩余不可还原原因。

## 分层识别清单

### 画布 / 设备

- 图片尺寸、目标 viewport、设备类型、DPR、裁切、安全区、滚动位置、浏览器/系统栏是否包含在截图中。
- 可见区域和不可见区域分开；不要把截图边界当页面真实边界。

### 布局 / 网格

- 页面主轴、内容最大宽度、左右边距、列数、gutter、固定区、滚动容器、层叠区、卡片密度。
- 映射到 4/8px scale 或项目 spacing token；像素不整齐时给近似和误差。
- 量测顺序：viewport → page shell → major regions → repeated groups → component internals → text baseline；先确定父级约束，再决定子项像素。
- 对齐规则：记录左/右/居中/基线/边缘对齐、equal gap、stack spacing、aspect ratio、min/max width、sticky/fixed/absolute 关系；不要只给单点坐标。

### 视觉量测与容差

- 输出 UI brief 时必须包含关键区域 bbox、主轴间距、字号/行高、圆角、边框、阴影、透明度、层级 z-order；无法精确量测时给区间、相对关系和置信度。
- 验收容差按区域定义：布局偏差默认 ≤4px 或按项目阈值，关键对齐/折行/截断单独验收；颜色用区域均值、ΔE 和人工复核组合判断，不用单像素决定全局。
- 对动态内容、动画、字体渲染、抗锯齿、设备 DPR、浏览器差异和压缩噪声设置忽略区或宽松阈值；阈值来源不明时标“需项目确认”。

### 组件 / 层级

- 组件树、组件职责、复用候选、变体、slot、嵌套关系、视觉优先级、主行动和次行动。
- 输出关键元素 bbox、中心点、层级、可点击性和置信度；同类组件优先匹配现有组件库或 Storybook。
- 同类组件是否一致；不一致时标设计特例或需确认。

### 文本 / OCR

- 原文、层级、字号估计、字重、行高、对齐、截断、换行、语气和可访问名称。
- OCR 低置信度文案必须标注；不得编造不可读文字。
- 图片内文字、第三方品牌标语、商品包装文字、人物证件/地址/订单号和被遮挡文本不直接复写；先做授权、隐私、OCR 置信度和是否真实 UI 文案判断。
- AI 生成图、低清截图和压缩长图里的伪文字只可作为视觉占位证据；实现时需替换为用户确认文案或项目真实数据。

### 颜色 / 字体 / 样式

- 背景、文本、边框、状态色、阴影、透明度、渐变、圆角、模糊、分割线和焦点态。
- 颜色受截图压缩、抗锯齿、透明叠加影响；hex 只能作为采样建议，优先映射项目 token。
- 颜色真值优先级：Figma variables / design tokens > 项目 CSS variables / theme config > DOM computed style > Storybook / 组件库文档 > 多点截图采样 > 单点截图采样 > 模型视觉判断。
- 字体推断记录 family 候选、系统 fallback、字重、字宽、x-height、baseline、字距、语言脚本和渲染平台；无字体文件或 computed style 时不得声称命中具体字体。
- 字号/行高用文本 bbox、高频样式聚类和项目 typographic scale 交叉验证；中文、英文、数字、emoji、图标字体需分开判断。

### 颜色识别高敏模式

- 触发：用户要求像素级还原、品牌色/状态色/暗色模式敏感、反复偏色、截图低清压缩、存在渐变/透明/阴影/blur/图片底色时启用。
- 先定目标：对齐设计源还是截图观感；Figma/DOM/token 与截图采样冲突时，设计稿还原优先 Figma，真实页面还原优先 DOM，组件迁移优先项目 token。
- 采样规则：同一色块多点采样，避开文字边缘、圆角、阴影、渐变过渡、透明层、压缩噪点和抗锯齿区域；记录 bbox、采样点、样本数、中位色/主色聚类、离群点和置信度。
- token 映射：按 raw/base → alias → semantic → component 分层；覆盖 brand、surface、text、border、status、chart、overlay、shadow、focus；实现优先改 token、CSS variables、theme 或组件 variant，禁止散落硬编码孤立 hex。
- 透明/渐变/阴影：区分 observed color 与 source color；半透明输出 base color + opacity 候选，渐变输出方向、stop 和置信度，阴影输出 x/y/blur/spread/alpha 候选；无法反推时标需 Figma/DOM 验证。
- 状态/主题：按钮、输入框、菜单、卡片、链接、标签等需列 default、hover、active、focus、disabled、selected、loading、error；light、dark、high contrast 分开，截图不可见状态不得脑补。
- 对比度：文本、图标、边框、focus ring、disabled 和 error 提示必须标 APCA/WCAG 风险；视觉还原与 a11y 冲突时列给用户/设计确认。
- 验收：颜色容差按区域设定；大面积纯色看区域均值/ΔE，品牌色和状态色更严格，文本另测 APCA/WCAG，阴影/渐变/透明层走人工复核或宽松阈值。
- 纠偏：每轮只改证据命中的 brand、surface、text、border、shadow、overlay 或 state color；输出元素/bbox、当前值、目标 token、偏差原因、最小修改点和复验截图，禁止整屏重写。
- 升级：两轮最小纠偏后仍偏色，停止主观调色，要求补 Figma Dev Mode、DOM computed style、品牌 token、原始无压缩截图或 Playwright 当前截图。

### 资产 / 图标 / 图片

- Logo、图标、插画、头像、商品图、背景图、视频封面、二维码、第三方品牌和版权资产。
- 标出需切图、需矢量化、可用图标库替换、必须授权或必须原创重绘的项。
- 资产默认做 replacement plan：真实 asset、图标库、原创重绘、占位符或需授权，不把截图裁片固化为交付资产。
- 资产清单至少包含 id、bbox、类型、来源、原始尺寸/倍率、裁切方式、透明度、圆角/遮罩、替换策略、授权状态和实现路径。
- 图标需记录语义、尺寸、描边、填充、视窗、旋转、状态色和是否品牌专属；通用 icon 才能用库替换，品牌/支付/平台图标必须查授权。
- 图片需区分内容图、装饰图、用户上传图和产品数据图；实现时定义 alt、object-fit、焦点裁切、加载/失败/占位/低网速状态。

### 状态 / 响应式 / 可访问性

- default、hover、focus、active、disabled、loading、empty、error、selected、pressed、expanded、readonly。
- 断点、container query、触控目标、键盘焦点、ARIA、对比度、RTL、深浅色和 reduced motion。
- 有 DOM 时优先核 accessibility tree、role/name/state/focus；截图只能提示可访问性风险，不能证明通过。
- 交互映射需覆盖点击、输入、拖拽、滚动、展开/收起、弹层、导航、校验、提交、撤销、关闭和加载反馈；不可见转场、接口、权限和埋点只能列假设。
- 对每个交互元素记录 role/name/state/value、hit area、focus order、键盘操作、读屏反馈、错误提示关联和 disabled/loading 行为。

### 响应式 / 平台安全区 / 可访问性门槛

- 截图只代表一个视口；必须列目标平台、最小/最大宽度、断点、container query、滚动区域、safe-area、DPR、横竖屏、键盘弹起和内容溢出策略。
- 用户未指定端和断点时，先给中立布局约束，不把单图绝对像素写成全端规则；移动端需关注系统栏、底部手势区、刘海/灵动岛/折叠屏和触控密度。
- 所有还原方案检查文本对比度、触控目标 44x44 等效尺寸、语义标题层级、表单 label、图片 alt、focus-visible、键盘路径、读屏名称、动态字体/缩放和 reduced motion。
- 若原图本身不达标，标“忠实还原风险”，同时给可访问替代方案；视觉还原与 APCA/WCAG 冲突时提交用户/设计确认。
- 状态矩阵至少覆盖核心 CTA、表单、列表、弹窗和导航的 default、loading、empty、error、disabled、hover、focus、pressed、输入中、校验失败、长文本、多语言、无图/坏图和弱网。

## 输出要求

1. 任务定位：图片类型、来源授权、目标产物、目标端/技术栈、允许近似程度和非目标。
2. 输入质量：清晰度、尺寸、裁切、DPR、是否低清、是否缺状态、是否需更多截图或 Figma/DOM 证据。
3. 视觉拆解：visual inventory、画布、布局、组件树、bbox、文本/OCR、颜色、字体、间距、圆角、阴影、图标、图片和资产。
4. 证据分层：图中可见、OCR、采样、项目规范、Figma/DOM/accessibility tree、用户确认、模型推测、需验证分开列。
5. UI brief：design tokens、组件 API、slots、状态矩阵、断点矩阵、a11y、资产替换计划和实现顺序。
6. 交互映射：可交互对象、role/name/state、触发动作、反馈、键盘路径、错误态、导航和不可见逻辑假设。
7. 验收标准：关键区域、viewport、截图对比方式、pixel diff、bbox deviation、颜色容差、人工复核点和不可还原项。
8. 固定模板：输入质量表、visual inventory、证据分层表、组件树、布局量测表、颜色采样表、token 映射表、状态矩阵、断点矩阵、交互映射表、资产清单、验收清单、缺口清单。
9. 合规清单：版权、商标、字体、图标、图片、肖像、隐私、竞品参考和授权边界。
10. 下一步技能：需要 a、u、b、i、aip、aie、rsch、law、端/语言、tst 或 aud 时写明触发原因。

## 约束

- 不承诺 pixel perfect；只有 Figma/DOM/token/字体/资产齐全且截图回归通过，才可说达到指定容差。
- 不把单张图推断成完整产品逻辑、权限、后端接口、埋点、状态机或响应式规则。
- 不复制未授权竞品页面、品牌资产、文案、图标、插画、字体或图片。
- 不忽略隐私；截图中的姓名、手机号、地址、订单、客户数据、内部系统信息必须脱敏或提醒处理。
- 不把 AI 生成图当真实 UI 规范；AI 图里的伪文字、伪图标、错位元素需要人工复核。
- 不绕开项目设计系统；共享组件、token、CSS variables、主题入口和消费方必须先查。
- 不把模型肉眼判断的颜色、单点截图采样或透明叠加后的 observed color 当设计源真值。
- 不用截图通过替代功能测试；视觉一致不代表交互、状态、数据和无障碍通过。
- 涉代码修改时必须进入对应端/语言技能，完成前由 aud 收口；核心路径加 tst。

## 高频 Bug 反例库

- 反例 1：凭感觉写 UI
   - 错法：看一眼截图直接写整页。
   - 对法：先输出画布、组件树、token、资产和不确定项。
   - 根因：未分层识别导致细节丢失。

- 反例 2：把截图像素当真值
   - 错法：所有尺寸按截图量出来硬编码。
   - 对法：映射 spacing scale、token、组件约束和响应式规则。
   - 根因：截图受 DPR、缩放、压缩和浏览器渲染影响。

- 反例 3：单图推断响应式
   - 错法：只有桌面截图就写移动端布局。
   - 对法：列断点假设和需补移动端截图；只能给响应式建议。
   - 根因：响应式是行为规则，不是单图事实。

- 反例 4：OCR 幻觉
   - 错法：看不清的字自行补完整。
   - 对法：低置信度标需确认，保留截图位置和候选。
   - 根因：不可读文本不能变成需求事实。

- 反例 5：图标库乱替换
   - 错法：随便找相似 icon。
   - 对法：标图标语义、尺寸、描边、来源和授权；必要时交 i。
   - 根因：图标既是语义也是品牌资产。

- 反例 6：字体伪还原
   - 错法：声称识别出具体字体。
   - 对法：列字体特征、fallback、需用户提供字体或 Figma 证据。
   - 根因：截图难以可靠识别 font family。

- 反例 7：颜色过拟合
   - 错法：采样一个像素作为品牌色，或把透明叠加后的截图色写成设计 token。
   - 对法：启用颜色识别高敏模式，多点采样、排除边缘噪声、映射语义 token，必要时补 Figma/DOM/品牌 token。
   - 根因：截图颜色是渲染结果，不等于设计源。

- 反例 8：忽略状态
   - 错法：只实现 default 状态。
   - 对法：列 hover、focus、disabled、loading、empty、error、selected 等状态缺口。
   - 根因：UI 可用性来自状态矩阵。

- 反例 9：忽略 a11y
   - 错法：为了像截图隐藏 label、焦点和对比度。
   - 对法：保持可访问名称、focus-visible、键盘路径和对比度。
   - 根因：视觉还原不能牺牲可用性。

- 反例 10：竞品一比一复制
   - 错法：照竞品截图复刻文案、图标、图片和品牌细节。
   - 对法：只借鉴信息层级和交互原则，做原创化改写。
   - 根因：版权、商标和不正当竞争风险。

- 反例 11：未跑截图回归就宣称完成
   - 错法：代码写完说已经像了。
   - 对法：同 viewport 截图，对比关键区域，列差异和未验证项。
   - 根因：视觉质量必须由图像证据收口。

- 反例 12：把 AI 图当设计稿
   - 错法：按 AI 海报里的伪 UI 细节做产品页面。
   - 对法：把 AI 图当视觉方向，重新定义真实组件、状态和可访问性。
   - 根因：生成图常有伪文字、伪控件和不一致布局。

- 反例 13：从截图脑补业务链路
   - 错法：看到按钮和列表就推断接口、权限、埋点和状态机。
   - 对法：只输出 UI 证据和交互假设；业务逻辑交给项目学习、端/语言和 API 技能验证。
   - 根因：截图只能证明可见界面，不能证明系统行为。

- 反例 14：没有 visual inventory
   - 错法：只描述“顶部导航、几个卡片”，漏掉分割线、浮层、徽标、禁用态和系统栏。
   - 对法：逐 region 盘点元素、bbox、层级、资产和交互属性，再生成组件树。
   - 根因：缺对象清单会让还原从第一步就漏件。

- 反例 15：量测只看单点像素
   - 错法：量一个按钮 x/y 后直接写 absolute 值。
   - 对法：先判断父容器、网格、gap、padding、baseline 和响应式约束，再映射 token。
   - 根因：布局是约束系统，不是散点坐标集合。

- 反例 16：裁截图当资产
   - 错法：把竞品 logo、商品图、插画或图标从截图里裁出来放进项目。
   - 对法：记录资产清单和授权状态，使用自有资产、授权资源、图标库或原创重绘。
   - 根因：截图可见不等于资产可用。

- 反例 17：交互从静态图脑补
   - 错法：看到 Tab、下拉和卡片就默认所有交互、路由和动画。
   - 对法：只映射可见可交互对象，隐藏状态和动作需 DOM、原型、多截图或用户确认。
   - 根因：静态图没有时间维度和业务规则。

- 反例 18：diff 只看整体分数
   - 错法：视觉回归总差异低就宣布通过。
   - 对法：拆 bbox、折行、颜色、z-order、遗漏/多余元素、a11y 和人工复核点。
   - 根因：小面积关键错误可能被整体像素分数稀释。

## 2024-2026 新坑速查

- screenshot-to-code 项目能生成初稿，但常缺少组件复用、设计系统、响应式、状态和 a11y；不能替代人工 brief 和回归。
- Figma/Dev Mode/variables 比截图可靠，但设计稿版本、隐藏图层、命名混乱和 token 映射仍需核实。
- OCR、PaddleOCR、Tesseract 等适合文字真值层，不适合推断组件语义和交互状态。
- OmniParser、ScreenCoder、UI grounding 等思路适合元素 bbox、中心点、层级和可交互区域识别，但不能直接保证工程质量。
- Playwright、Storybook、BackstopJS 等视觉回归适合作为验收证据，但动态内容、字体差异、动画和抗锯齿会产生噪声；必须定义 golden screenshots、阈值、更新条件和人工审批。
- 浏览器 computed style 只适用于自有或授权页面；不得绕过登录、付费墙、风控或抓取第三方私有资产。
- 多模态模型看图能力增强，但仍容易误判精确像素、字体、色值、图标、隐藏状态和响应式；复杂链路需沉淀截图-brief-实现-渲染截图-人工评分样本做回放。
- 设计系统迁移时，视觉相似不等于代码可维护；token、component API、slots、组件相似度和状态矩阵优先于硬编码。
- 竞品参考合规压力上升；输出必须保留原创化变化和授权缺口。
- AI 生成 UI 图常含伪文字、伪图标、不可实现布局和无效状态，必须先转成真实 UI 规范。

## 与相邻技能的边界

- 本技能负责：图片/截图/设计稿到 UI brief、视觉拆解、组件树、token 建议、资产清单、状态矩阵、断点矩阵、验收标准和截图回归差异分析。
- 不负责：品牌战略和首屏方向 → b；信息架构、组件 API、状态模型和多端架构 → a；视觉落地、CSS/token 细节 → u；图标绘制和 SVG 系统 → i；AI 生图 prompt → aip；多模态模型、OCR/解析管线和 eval 系统 → aie；外部工具/开源方案查证 → rsch；版权、商标、肖像和竞品合规 → law；代码实现 → 对应端/语言技能。
- 协作：先用 image-to-ui 把图变成证据化 UI brief；再交设计链和端/语言实现；实现后用截图回归和 aud 收口。
