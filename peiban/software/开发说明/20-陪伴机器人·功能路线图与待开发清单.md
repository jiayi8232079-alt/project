## 0. 一句话判断

**机器人现在是"图纸齐全，但还没通电"。** 证据（基于现有代码）：

| 维度 | 现状 |
|---|---|
| 固件 | ❌ 未开发（`firmware-companion-t5` 待建仓库，见 `09` §5） |
| 涂鸦真接入 | ❌ OpenAPI / Pulsar 全 mock（`09` §3/§6） |
| MCP 13 工具 | 🟡 全 mock 假数据（`08` §3，`companion-tools.service.ts`） |
| 记忆 / 人格 / 故事 | 🟡 刚设计完（文档 `19`），尚未建表与编码 |
| 声纹成员 / 家庭任务 | ❌ V4.3 核心能力，尚未落地 |
| 社区内容 / 生活服务 / 医院协同 | ❌ V4.3 商业闭环，尚未形成机器人播报与任务执行闭环 |
| 保命双链路 | 🟡 设计就绪，SOS、视觉跌倒事件接入、推送、视频复核、社区/人工升级未完整落地 |

**所以第一优先级不是加花哨功能，而是把"能开口、能联网、能保命、能查真数据"这条最小可用链路打通。别广度铺功能，要深度跑通一条线。**

## 1. 优先级框架（绑定商业模型）

商业闭环：**家庭入口 → 信任 → 诊后管理 → 长期照护复购**（见 `15`）。据此排序：

| 优先级 | 含义 | 对应商业价值 |
|---|---|---|
| **P0** | 让机器人"能用"的最小链路 | 入口能不能用（生死线） |
| **P1** | 陪伴体验 + 健康闭环 | 留存壁垒（陪伴）+ 家属付费意愿（健康） |
| **P2** | 商业化 / 家属侧 / 规模化 | 放大与变现 |

North Star（陪伴侧）：**老人周主动对话天数**；护栏：记忆错误率、情感依赖投诉、隐私越界、家属满意度、AI 成本延迟。

## 6. 重点展开 ① · 家属远程"投喂"（mini-spec）

> 让异地子女能**隔空给机器人下达关怀指令**，机器人替子女去陪/去提醒老人。这是把"家属牵挂"变成可执行动作，极强家庭粘性，也直接服务"异地子女"这个付费决策人。

### 6.1 典型场景（JTBD）
- "提醒我妈今天多喝水 / 别忘了下午复诊。"
- "替我跟我爸说一声生日快乐。"
- "我这周末回去看他，帮我先跟他说一下，让他高兴高兴。"
- "我妈最近情绪不好，你多陪她聊聊。"

### 6.2 两种下发模式
| 模式 | 触发条件 | 流程 |
|---|---|---|
| **A. 即时播报** | 机器人在线且老人在旁 | 家属 App 下发 → 后端 → 涂鸦 OpenAPI 下行 → 机器人主动播报「您闺女让我跟您说…」 |
| **B. 待机融入** | 机器人离线 / 老人不在 / 勿扰时段 | 写入 `companion_memory(kind=family_message, followUpAt)` → 下次会话开场由 `recall_memory` 自然带出 |

### 6.3 落点
- 后端：新增 `family/family-message` 端点 + `queue`(bullmq) 异步派发；复用 `notification`/`realtime`。
- MCP：新增 `get_family_messages`（读，喂开场简报）；即时播报走 device 下行而非 MCP。
- 数据：`companion_memory.kind='family_message'`（plane=companion），或独立轻表 `family_care_message`（含 fromFamilyMemberId/mode/status/playedAt/elderResponse）。

### 6.4 规则与护栏
- **身份鉴权**：仅该老人**已绑定家庭成员**可下发（复用 `family_member` 权限）。
- **限频 + 勿扰**：单家属/天上限；夜间/午休勿扰时段顺延为模式 B。
- **内容安全**：过内容过滤，禁敏感/诱导；不冒充老人本人。
- **回执闭环**：播报后给家属回执（已播报 / 老人有无回应 / 老人情绪），让"投喂"有反馈，强化复用。
- **AI 表达**：以"小孩/孙辈"口吻转达，温暖自然，不生硬念稿。

### 6.5 验收
- [ ] 在线即时播报到达 < 5s；离线转模式 B 不丢失。
- [ ] 非绑定家属无法下发（越权 100% 拦截）。
- [ ] 勿扰时段不打扰；超频被限。
- [ ] 家属能收到"是否已转达 + 老人反应"回执。

## 7. 重点展开 ② · 内容生态（mini-spec）

> 戏曲、评书、广播剧、老歌、新闻、健康科普音频——这是老人**最高频的主动需求**，也是把机器人从"偶尔聊两句"变成"每天都开着"的日活引擎。

### 7.1 内容类型与来源
| 类型 | 来源 | 版权策略 |
|---|---|---|
| 戏曲/评书/广播剧/老歌 | 第三方授权内容 API / 电台聚合 | **必须授权**，标注来源 |
| 新闻/天气播报 | 现有 `get_weather` + 新闻源 | 授权源 |
| 健康科普音频 | 自有知识库（涂鸦 RAG 已有通道） | 自有 |
| 个人化故事 | 文档 `19` `tell_story`（怀旧） | 自有 |

### 7.2 点播流程
```
老人："给我来段京剧" / "放首邓丽君" / "讲讲新闻"
  → 语音 → 智能体识别意图
  → play_content(category, keyword?)  (新 MCP 工具)
     ├─ 查内容目录（list_content_catalog）
     ├─ 命中 → 端侧播控（涂鸦内置 播控 MCP / cmd_cb）开始播放
     └─ 未命中 → 婉拒 + 推荐相近（基于 companion_memory 偏好）
  → 播放中可语音「暂停/继续/换一个/大点声」→ pause_content / 播控指令
  → 记录偏好 → save_memory(kind=preference,"爱听京剧")，下次主动推荐
```

### 7.3 落点
- MCP：新增 `play_content` / `pause_content` / `list_content_catalog`（读为主；播控走端侧）。
- 后端：`content` 模块（新）做内容目录 + 授权源适配 + 用量计量（计费/版权结算）。
- 端侧：复用涂鸦 Wukong 3.0 内置「播控 MCP」；固件支持音量/暂停/续播。
- 个性化：基于 `companion_memory(kind=preference)` 主动推荐（"今天给您来段您爱听的越剧？"）。

### 7.4 规则与护栏
- **版权合规**：只用授权内容源，记录来源与授权；转 `legal-counsel` 复核。
- **适老交互**：语音控制为主，音量/语速适老；一句话能点播、能停。
- **健康融合**：长时间播放后温和提醒休息/活动；睡前自动降音渐停。

### 7.5 验收
- [ ] 语音点播命中率达标；未命中有相近推荐。
- [ ] 播控（暂停/续播/音量/换一个）语音可控。
- [ ] 偏好被记住并主动推荐。
- [ ] 内容来源授权可追溯、用量可计费。

## 8. 建议开发顺序（强烈建议按此走）

```
第一步：P0 全部           → 打通"能开口/联网/保命/查真数据"最小可用链路
第二步：P1 声纹+陪伴       → 声纹成员识别 + 长期记忆 + 人格 + 主动惦记
        P1 用药/跌倒闭环   → 健康与安全闭环起步（家属付费抓手）
第三步：社区样板           → 社区内容触达 + SOS/跌倒处置 + 试点报表
第四步：服务协同放大       → 家属投喂、内容生态、生活服务、合作医院、情绪监测
```

> 内容生态(§7)与家属投喂(§6)虽列 P2，但**商业/粘性价值很高**：建议在 P0 跑通、P1 陪伴上线后**优先插队**，与情绪监测一起作为"放大留存与家属付费"的组合拳。
